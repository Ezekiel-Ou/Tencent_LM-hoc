**不做的事**（来自冠军经验，1v1 上明确无效或反向）：
- 不加 `assist`、`teamspirit`（1v1 没队友）
- 不加 multi-head value（与冻结网络冲突）
- 不动 `GAMMA` 锚点 0.995 → 直接跳 0.998（应渐进，否则训崩）
- 不加 PopArt 单 value head（与 advantage normalization 冗余，详见 §2.5）

## 2. 奖励权重优化

### 2.1 数值调整建议（一次性 B 类改动）

```python
# 仅给出需要改动的 key，未列的保持原值。所有权重均为 v3 起步值，后续按 §3 课程切换。
REWARD_WEIGHT_DICT = {
    # 不变：tower_hp_point=6.0, hp_point=2.0, last_hit=0.5, ep_rate=0.25,
    #       money=0.004, exp=0.004, death=-1.0, cleanse_success=0.15,
    #       skill_hit_enemy_hero=0.15, recover_skill_low_hp=0.3, safe_last_hit=0.15

    "kill":         0.8,   # 0.6 → 0.8  鼓励更主动的击杀，1v1 击杀=最大优势
    "forward":      0.05,  # 0.2 → 0.05 与冠军 baseline 0.01 对齐，避免压过 KDA
                           # 注：保留 REMOVE_FORWARD_AFTER=1000 的硬截断（开局上线引导）
    "cake_pickup":  0.3,   # 0.8 → 0.3  单事件不应大于一次击杀
}
# 配套：把 reward_process.py:565 的 `if hp_rate >= 1.0` 改为 `if hp_rate >= 0.9`
#       —— 满血/近满血吃饼是浪费再生资源，应只在真的需要时奖励
```

**为什么 kill 提到 0.8 不到 1.0**：1v1 整局击杀次数本就不多（典型 1-5 次），权重再高会让前期 farming 完全被压制；0.8 = |death| × 0.8，保持 kill < |death| 的不对称（防送头），又比原来的 0.6/1.0=0.6 拉近，让"换 1:1 略亏、换 2:1 大赚"形成更明显的引导。**death 保持 -1.0**：v1 已在这个尺度上稳定 30h，不动可以避免 critic 重估期的胜率回退。

**为什么 forward 降到 0.05**：当前 0.2 比 last_hit (0.5) 的 1/2.5、比 hp_point (2.0) 的 1/40，但 `forward` 几乎每帧都有非零差分（位置变化），实际累加贡献会远超稀疏的 kill / last_hit；这是常见的"看着权重小、累积淹没稀疏信号"陷阱。**`REMOVE_FORWARD_AFTER = 1000` 不动**：这条规则的设计目的是"开局让英雄从泉水上线"，1000 帧后撤掉避免无脑前压脱塔被反打。

**为什么 cake_pickup 加 hp<90%**：当前判定 `hp_rate >= 1.0` 才不给奖励（`reward_process.py:565`），导致 99% 血也奖励一次吃饼。但血量饼是有再生 CD 的稀缺资源（75s 一次），满血/近满血吃等于浪费，应该惩罚（不给 reward 等价于变相惩罚）。`< 0.9` 保留了"轻微换血后及时回血" 的合理诉求，又过滤了"满血贪饼" 的劣行。

**为什么不引入 `attack_hero` 输出量奖励**：当前 `skill_hit_enemy_hero` 已经捕捉了关键输出事件，再加 dense damage 容易触发 reward hacking（蹭血换 reward）。冠军原文也提到"过分追求微操可能损失其他能力"。

### 2.2 缺失但建议加入的奖励项（B 类 warmup）

按收益排序，每次只加 1 项并跑 4-8h 对照实验：

| 新 reward key | 权重 | 触发条件 | 解决什么问题 |
|---|---|---|---|
| `no_op_streak_penalty` | -0.1 | 连续 5 帧 `button=NONE` | 站桩问题。冠军用 action constraint loss 解决，这里用 reward 形式更轻量 |
| `under_own_tower_safe` | +0.05 | 残血（hp_rate<0.3）且在自塔范围内 | 鼓励残血回塔，与 `recover_skill_low_hp` 互补 |
| `tower_dive_success` | +1.5 | 在敌塔范围内击杀敌方英雄（追击成功） | 强化塔下追击的高难收益场景 |
| `tower_dive_death` | -2.0 | 在敌塔范围内被击杀（强塔下送头） | 抑制送塔行为；与 death 叠加 |

**说明**：
- `no_op_streak_penalty` 不需要时序情景奖励逻辑（user 说有问题再加），可在 `reward_process.py` 用 `self._consecutive_noop_frames` 状态变量实现，<30 行代码。
- 后三项属于"用户自行观察录像后再决定"的情景奖励范畴，**本方案只占位、不强加**，等录像发现"模型不会塔下追击"或"模型频繁送塔下"再开启。

### 2.3 时间衰减重设计（B 类）

当前 `TIME_SCALE_ARG=8000`，整体 `0.6^(f/8000)` 衰减：8000 帧时已衰减到 0.6，20000 帧时（一局最长）衰减到 ~0.13。**问题**：这把胜负关键的稀疏奖励 `kill / death / tower_hp_point` 也压平了，与冠军经验"KDA 整局都很重要不衰减"矛盾。

**改造方案**：每个 reward key 独立时间衰减系数（小改 `reward_process.py:273-275`）：

```python
# 新增配置
REWARD_TIME_SCALE_OVERRIDES = {
    "kill":           0.0,   # 不衰减
    "death":          0.0,   # 不衰减
    "tower_hp_point": 0.0,   # 不衰减
    "cleanse_success":0.0,   # 不衰减（稀疏事件）
    # forward 不在表里：沿用 TIME_SCALE_ARG=8000 + REMOVE_FORWARD_AFTER=1000 的现有逻辑
    # 其余项沿用 TIME_SCALE_ARG=8000
}
```

时间衰减实现处（`reward_process.py:274`）改为：

```python
scale_arg = REWARD_TIME_SCALE_OVERRIDES.get(reward_name, self.time_scale_arg)
time_scale = 1.0 if scale_arg == 0 else math.pow(0.6, float(frame_no) / scale_arg)
```

**`REMOVE_FORWARD_AFTER` 保持原 1000 帧硬截断**——它的目的是"开局上线引导，到 1000 帧（≈33s）英雄已经上线，撤掉避免无脑前压"；不要改成 ramp-down，否则会鼓励 1000-6000 帧的脱塔前压。

### 2.4 零和与情景奖励的边界（设计稳定位点）

**零和已经实现**（`reward_process.py:263-271`）：所有"非主侧专属" reward 走 `main - enemy` 差值，确保 `Σreward = 0`。这是 1v1 镜像图防双方挂机的核心机制，不要改。

**主侧专属 reward**（如 `cake_pickup`、`recover_skill_low_hp`、`safe_last_hit`）天然不对称，这是合理的，因为对手"没拿吃"也不算损失。但要注意：

- 主侧专属正向 reward **总和不能超过零和 reward 量级**，否则会破坏零和性 → 当前 `cake_pickup=0.8` 偏大就是这个隐患，建议降权（§2.1）。
- 后续加情景奖励时，**正负成对加**（夸张正值 + 对称负值），避免一方面 reward 持续走高破坏 critic 学习。

### 2.5 奖励归一化：要不要加 PopArt？

**不加**。原因：
1. `algorithm.py` 已经做了 `USE_ADVANTAGE_NORM=True`，advantage whitening 吃掉了"整体奖励缩放"的自由度
2. PopArt 的真正价值在 multi-head value（每个 reward 子项一个 value head，绝悟 NeurIPS 2020 §3.2），这要求改网络结构 → 与冻结锚点冲突
3. 单 value head + 标量 reward + advantage norm 的组合下，PopArt 收益几乎为 0（Liu 2023 实证）

**真正建议加的**：`return running std` 归一化，即把 GAE 计算后的 `reward_sum` 用滚动方差归一化。代码改动小（algorithm.py 里维护一个 `running_var`），对训练稳定性的提升明确，是 A 类修改。

```python
# algorithm.py 在 reward 输入 critic 前
if not hasattr(self, "_return_rms"):
    self._return_rms = RunningMeanStd()
self._return_rms.update(reward.detach().cpu().numpy())
reward = reward / (np.sqrt(self._return_rms.var) + 1e-8)
```

### 2.6 其他非情景 reward 设计补充

以下 5 类来自外部 reward 设计文献和大规模 RL 系统经验，**与"录像情景定向 reward shaping"正交**——是 reward 形式本身的补充而非新场景。按 ROI 排序。

#### 2.6.1 终局胜负 reward（B 类，ROI 高，强烈建议）

**现状问题**：当前所有 reward 都来自帧间差分（`reward_process.py:get_reward` 全部基于 `cur_frame_value − last_frame_value`），**没有"任务结束时 ±R" 的终局稀疏信号**。HoK Arena 5 分量标准、OpenAI Five、AlphaStar 都有终局 reward；这条是项目当前与冠军基线对比真正缺失的一项。

**改造**：

```python
# conf.py:GameConfig 加 2 项
REWARD_WEIGHT_DICT = {
    # ... existing 12 ...
    "win":   5.0,
    "lose": -5.0,   # 实际只用一个 key 即可：win=±5，胜局 +5、败局 -5
}

# reward_process.py 在 game over 信号触发的最后一帧把 win/lose 加进 reward_dict
# 信号来自 workflow，env_obs["terminated"] / "truncated" + win 标志（observation.win）
```

**数值合理性**：γ=0.995 下 +5 终局奖励反传到第 0 帧仍有 `5 × 0.995^2000 ≈ 2×10⁻³` 量级 — 不大但**对齐"什么才是最终目标"**。tower_hp_point 整局累积大致是 6.0 量级，win/lose 设 5 让二者同量级，相互不淹没。

**价值**：压制中段 reward hacking 风险。当前虽然 reward 设计已经接近最优，但如果未来加入"情景奖励"且数值不当，仍可能出现"刷 reward 不打塔"的退化；终局 reward 是终极锚点。

**实现位点**：`workflow/train_workflow.py:209-220` 已有 `is_gameover` 分支和 `env_obs["observation"][i]["win"]` 字段（见 `开发指南/环境详述.md:108`），直接在此处把 win/lose 注入最后一帧 reward 即可，~10 行。

**续训类别**：B（warmup），新增 reward key 会改变 reward_sum 分布，但 value head 共享，warmup 1-2h 即可。

#### 2.6.2 情景化权重衰减（B 类，ROI 中-高）

**来源**：`reward3.md` "方式三"。**与"新增 reward 场景项"正交**：不引入新 key，只让现有 reward 项的权重随当前状态动态变化。冠军 3v3 实测有效。

**1v1 适配场景**（按可落地性排序）：

| 触发条件 | 权重调整 | 教育意图 |
|---|---|---|
| `hp_rate < 0.3`（残血） | `money/exp` 权重 × 0.1<br>`forward` 权重 × 0.5 | 残血时不应贪兵线，应撤退/回塔 |
| `enemy_hero.hp_rate < 0.2`（敌方残血可击杀） | `kill` 权重 × 1.5<br>`forward` 权重 × 1.5 | 残血敌方在视野时应追击 |
| 自塔 hp < 0.5（劣势期） | `forward` 权重 × 0.3<br>`hp_point` 权重 × 1.5 | 自塔危险时优先防守 |
| 敌塔 hp < 0.3（终局推塔期） | `tower_hp_point` 权重 × 2.0<br>`death` 权重 × 0.7 | 临门一脚可承担更高死亡风险 |

**实现**：`reward_process.py:get_reward` 中每帧根据状态选择 weight multiplier：

```python
def _dynamic_weight_multiplier(self, reward_name, main_hero, enemy_hero, main_tower, enemy_tower):
    multiplier = 1.0
    hp_rate = _safe_div(_get(main_hero, "hp", 0), _get(main_hero, "max_hp", 0))
    enemy_hp_rate = _safe_div(_get(enemy_hero, "hp", 0), _get(enemy_hero, "max_hp", 0))
    enemy_tower_rate = _safe_div(_get(enemy_tower, "hp", 0), _get(enemy_tower, "max_hp", 0))

    if hp_rate < 0.3:
        if reward_name in ("money", "exp"): multiplier *= 0.1
        if reward_name == "forward":        multiplier *= 0.5
    if enemy_hp_rate < 0.2 and enemy_hp_rate > 0:
        if reward_name == "kill":           multiplier *= 1.5
        if reward_name == "forward":        multiplier *= 1.5
    if enemy_tower_rate < 0.3 and enemy_tower_rate > 0:
        if reward_name == "tower_hp_point": multiplier *= 2.0
        if reward_name == "death":          multiplier *= 0.7
    return multiplier
```

调用点在 `get_reward()` 算 `reward_struct.value * reward_struct.weight * time_scale` 时再乘 `multiplier`。

**风险**：权重动态变化会让 critic 学习目标变 non-stationary。控制方式：multiplier 不要超出 [0.1, 2.0] 范围；切换都在"明显可识别状态" 触发，避免频繁微小波动。

**续训类别**：B，与 §3.1 三段式权重调度配合时注意 multiplier 是乘在三段式之后的（multiplicative，不是加法）。

#### 2.6.3 Potential-Based Reward Shaping（PBRS，A 类，ROI 中）

**理论**：Ng et al. 1999 证明，形如 `F(s,a,s') = γΦ(s') − Φ(s)` 的 reward shaping **不改变最优策略**（保证最优解不变）。这是理论上唯一"严格无害"的 shaping 框架。

**应用：替代 `forward`**：当前 `forward` 是 `progress(t) − progress(t-1)`，其中 `progress = 1 − dist_hero2enemy/dist_main2enemy`（`reward_process.py:200`）。改成 PBRS 形式：

```python
# reward_process.py:calculate_forward 改造
def calculate_forward_pbrs(self, main_hero, main_tower, enemy_tower, gamma=0.995):
    if main_hero is None or main_tower is None or enemy_tower is None:
        return 0.0
    hp_rate = _safe_div(_get(main_hero, "hp", 0), _get(main_hero, "max_hp", 0))
    if hp_rate <= 0.0:
        return 0.0
    hero_pos = _loc(main_hero)
    enemy_tower_pos = _loc(enemy_tower)
    map_diag = math.dist(_loc(main_tower), enemy_tower_pos) + 1.0
    Phi_cur = -math.dist(hero_pos, enemy_tower_pos) / map_diag   # 越靠近敌塔 Φ 越大
    Phi_last = getattr(self, "_last_Phi", Phi_cur)
    self._last_Phi = Phi_cur
    return gamma * Phi_cur - Phi_last
```

**对比当前 forward**：数学等价上接近（都是"推进 delta"），但 PBRS 形式有理论保证 + 自动包含 γ 权衡。**实际效果差距可能很小**，这条优先级低于 2.6.1 / 2.6.2。

**为什么仍然推荐做**：当前 `forward = progress(t) − progress(t-1)` 实际上是 PBRS 的退化形式（Φ = progress、γ_implicit = 1）。改成 `γΦ(s') − Φ(s)` 是 5 行改动，几乎零成本，理论更干净；同时**`REMOVE_FORWARD_AFTER=1000` 仍然保留**（PBRS 不消除"上线引导是阶段性任务"这件事）。

**续训类别**：A（数值小幅变化，热启动即可）。

#### 2.6.4 镜像数据增强（A 类，ROI 中）

**来源**：AlphaStar / OpenAI Five 都用，1v1 镜像地图天然适用。**与 reward 设计正交**——不动 reward 内容，只在样本生成层把每条样本"红蓝镜像"得到一条新样本，免费 2× 训练数据。

**当前状态**：`agent_diy/feature/feature_process.py` 已经做了**单边镜像**（红方坐标取负、特征对齐到蓝方视角），这是必要的对齐处理；但**没做"额外的样本翻倍增强"**。区别如下：

| 概念 | 当前已有 | 本节建议新增 |
|---|---|---|
| Camp normalization | ✅ 红方坐标镜像到蓝方视角 | — |
| Data augmentation | ❌ | 每条样本生成时再做一次 x ↔ -x 的样本，组成 2× batch |

**实现**：`agent_diy/feature/definition.py:sample_process` 中，对每个生成的样本：
1. 复制一份样本
2. 把样本中所有 x 坐标取负、move_x 和 skill_x 的 action label 做对称翻转（i ↔ 15-i）
3. 把镜像样本和原样本一起进 buffer

**注意点**：
- legal_action 和 sub_action_mask 也要相应翻转
- LSTM hidden state **不能镜像**（hidden state 是网络状态，不是空间特征）
- 增强后样本数翻倍，learner 端 batch 不变意味着每个原始样本被覆盖的次数减半 → 训练步数可保持不变

**预期收益**：critic 收敛更快（同样的"位置"概念有 2× 数据点）、模型对左右对称性的偏置更小。AlphaStar 论文消融实验显示 +3-5% 胜率。

**续训类别**：A（不改 reward / 不改网络 / 不改采样维度，只是 buffer 里多一倍样本）。

**工程风险**：实现要小心 — 坐标翻转和动作 label 翻转必须严格一致，**改完一定要写单元测试**：对一条 obs，做镜像 → 网络前向 → 期望输出 logits 经过相应翻转后与原 obs 输出一致（容差 1e-6）。这是冠军 reward3.md 里"代码 review 灾难"的同类陷阱。

---

#### 2.6.5 Self-Imitation Learning（SIL，A 类，ROI 低）

**来源**：Oh et al. ICML 2018 *Self-Imitation Learning*。把历史高 reward episode 存进 buffer，定期用监督学习 loss（behavior cloning）让当前 policy 模仿这些高分轨迹。

**机制**：
```python
# 1. 维护一个 priority replay buffer，保存历史 reward_sum 排前 K% 的 episode
# 2. 每 N 个 PPO 更新做 1 次 SIL 更新：
#    loss_sil = -log π(a|s) * max(R - V(s), 0)
#    含义：只在"该状态下旧策略表现优于当前 critic 估计"时才模仿，避免学到次优
# 3. SIL loss 加到总 loss 上，权重 ~0.1
```

**1v1 上的预期收益**：
- 加速从 common_ai 阶段学到的"基本套路"（补刀、上线、塔下击杀）的复现
- 末期 self-play 出现退化时能从历史强样本"找回"丢失的能力

**为什么 ROI 低**：
- 开悟当前是 on-policy PPO 框架，引入 off-policy SIL buffer 需要在 algorithm.py 和 sample 管线两处改 — **工程量约 100-150 行**
- 1v1 单卡训练规模下，纯 PPO + PFSP 对手池其实已经能解决"防遗忘"问题（§3.4 / §4.3）
- SIL 真正发挥价值是在 sparse reward / hard exploration 任务上（如 Atari Montezuma），MOBA 有 dense reward，边际收益小

**续训类别**：A（不破锚点），但**不建议优先做**。如果做，放在 v3.3+ 由用户决定。

**实施提示**：如果做，最小可行版本不必引入 priority replay：直接维护一个"最近 50 个胜局" 的 FIFO，每 10 个 PPO 步对它们做一次小 batch 的 BC loss 即可（权重 0.05-0.1）。

## 3. 训练流程 / 课程设计

### 3.1 三段式权重调度（B 类，warmup 续训）

参考冠军原文「课程训练前期重发育，后期可调高稀疏奖励」+ 绝悟 CSPL + OpenAI Five γ 渐进，建议：

| 阶段 | 训练步数估计 | hp | tower_hp | money/exp | kill | death | forward | last_hit | cake |
|---|---|---|---|---|---|---|---|---|---|
| **EARLY**（发育） | 0–5k step | 2.0 | 5.0 | **0.006** | 0.5 | -1.0 | 0.05 | 0.6 | 0.3 |
| **MID**（均衡，当前 v2 用这套） | 5k–25k | 2.0 | 6.0 | 0.004 | 0.8 | -1.0 | 0.05 | 0.5 | 0.3 |
| **LATE**（嗜血 + 推塔） | 25k+ | 1.5 | **7.0** | 0.003 | **1.0** | -1.0 | 0.02 | 0.3 | 0.2 |

**实现**：在 `agent_diy/conf/conf.py:GameConfig` 加 3 套字典 `REWARD_WEIGHT_EARLY / MID / LATE`，在 `reward_process.py:GameRewardManager.__init__` 读取一个全局 step（通过 monitor 或单独 mmap 文件），动态选择。切换时**临时把 lr 砍半 1-2 小时**渡过 critic 重估期，否则会出现胜率短暂回退。

**为什么不一次性用 LATE 权重**：早期没有"发育"基础就强逼击杀，模型会学到无脑近战导致 hp_point 反向收益爆炸；冠军原文明确踩过这个坑。

### 3.2 PPO 超参的课程调度（A 类）

把现有"线性 lr + 指数 entropy" 升级为三阶段：

| 超参 | EARLY | MID | LATE | 实现位置 |
|---|---|---|---|---|
| `GAMMA` | 0.995 | 0.997 | 0.998 | `conf.py:GAMMA` 改为按 step 读 |
| `LAMDA` | 0.95 | 0.96 | 0.97 | 同 |
| lr | 3e-5 → 1e-5（5k 步线性） | 1e-5 常数 | 1e-5 → 3e-6（再 5k 步线性） | `algorithm.py:scheduler` 改成自定义 lambda |
| entropy β | 0.01 | 0.005 | 0.002（不低于 0.001） | `algorithm.py:75` 已经在指数衰减，把 floor 调到 0.001 |
| `BETA_END` | — | — | 0.001（绝对下限） | `Config` 加常量 |

**γ 渐进**是 OpenAI Five 的关键经验：γ 从 0.995 直接跳 0.998 会让 critic 的目标值范围放大近 2 倍，触发训练崩溃；务必渐进（每次切换前对照 value_loss 曲线是否平稳）。

**lr 不要低于 3e-6**：冠军原文明确 "再低 float32 精度不够会白训"，3e-6 是硬下限。

**entropy floor 0.001**：开悟环境动作空间大（12×16×16×16×16×9），entropy 跌穿 0.001 会让模型完全确定性，遇到对手分布偏移直接崩。

### 3.3 阶段切换的客观信号

不要按"训了多久"切，按胜率/loss 切：

| 切换 | 信号 | 阈值 |
|---|---|---|
| EARLY → MID | vs common_ai 胜率 | ≥ 75% 持续 1h |
| MID → LATE | vs 最新自身 selfplay 胜率 | 稳定在 45-55% 区间 1h（self-play 已经在 Nash 附近） |
| LATE → ROLLBACK | value_loss 暴涨 / KL>0.3 持续 30 min | 退回 MID，lr 砍半重训 2h |

监控字段已在 `algorithm.py:103-105`（mean_ratio, approx_kl, clip_fraction）和 `train_workflow.py:227-241`（reward_xxx, action_xxx, kill, death, tower_hp）就位，**不需要新加代码**，只需把这些字段在监控面板上配出来。

### 3.4 防遗忘与抗退化（A 类）

冠军经验和 AlphaStar/OpenAI Five 都提到：**纯 self-play 末期会出现"看不懂脚本"的灾难性遗忘**。两层防护：

1. **混合采样保留 common_ai**：当前 `mixed` 配置里 common_ai 占 0.05，建议 LATE 阶段提到 0.10-0.15
2. **历史 pinned checkpoint 永不下架**：详见 §4.3

## 4. Self-play 对手池设计

### 4.1 现状 mixed 配置审视

当前权重 `[selfplay 0.55, 263170 0.25, 263062 0.15, common_ai 0.05]`：
- ✅ 比例分布合理（最新 + 历史 + 弱基线）
- 🔴 **静态权重**，不会因为"对 263170 已经胜率 90%"而降低对它的采样；后期算力浪费在打弱
- 🔴 缺少"按对位胜率反馈"的动态调整
- 🔴 历史 model_id 没有"角色定位"（哪个是 anti-style？哪个是 pinned-strong？）

### 4.2 半 PFSP 采样（A 类）

完整 PFSP 需要维护胜率矩阵，工程量大；用**简化版**：

```python
# env_conf_manager.py 内追加
class OpponentPool:
    """简化 PFSP：按 (1-winrate)^p 重新权衡 mixed 权重，每 N 局更新一次。"""
    def __init__(self, base_types, base_weights, p=1.0, alpha=0.7):
        self.types = base_types
        self.base = base_weights        # 用户配置的先验权重
        self.winrate = {t: 0.5 for t in base_types}  # 滑动估计
        self.episode_count = {t: 0 for t in base_types}
        self.p = p
        self.alpha = alpha              # 先验 vs 反馈混合

    def update(self, opponent_type, win):
        self.episode_count[opponent_type] += 1
        n = self.episode_count[opponent_type]
        lr = 1.0 / min(n, 100)          # 滚动均值，上限 100 局窗口
        self.winrate[opponent_type] = (1-lr) * self.winrate[opponent_type] + lr * win

    def sample_weights(self):
        weights = []
        for t, base_w in zip(self.types, self.base):
            pfsp_w = max(1.0 - self.winrate[t], 0.05) ** self.p
            weights.append(self.alpha * base_w + (1-self.alpha) * pfsp_w)
        return weights
```

每局结束后 `pool.update(opponent_type, win=1/0/0.5)`，每 `update_config` 时调用 `pool.sample_weights()` 替换 `opponent_agent_weights`。

**参数取值**：
- `p=1.0`（AlphaStar 默认；`p=2` 太聚焦"打不过的硬骨头"，1v1 资源紧不建议）
- `alpha=0.7`（先验权重占 70%，反馈占 30%，避免抖动太大）
- 窗口 100 局（开悟约 1-2h 一局，100 局 ~ 100-200h，与训练总周期匹配）

### 4.3 `kaiwu.json` 三个模型槽的最优分配

平台限制最多 3 个 model_id。建议分配：

| 槽位 | 角色 | 选取标准 | 更新策略 |
|---|---|---|---|
| 槽 1 | **Pinned Strongest** | 当前训练以来对 common_ai 胜率最高、对自身胜率均衡的 checkpoint | **永不替换**（直到下一大版本 v4+） |
| 槽 2 | **Mid Snapshot** | v1 训完 30h 的那版 / 训练总时长的 1/3 处的 checkpoint | 每 1-2 周替换为新的"中段强者" |
| 槽 3 | **Anti-Style / Fresh Pool** | 最近 48h 内某次大幅调整奖励的 checkpoint，或与主模型风格差异最大的 | 每 1-2 周替换 |

**槽 1 的意义**：模型坍缩到 rock-paper-scissors 时，pinned-strongest 是唯一"知道怎么赢" 的锚点，强迫主模型不能放弃基础能力。AlphaStar 的 Main Agent ↔ Main Exploiter 关系的最小裁剪版。

**当前 263170 / 263062 / 255479 三个 ID 怎么定位**：建议用户跑一次三方对战（直接用现有 eval 流程），看：
- 哪个对 common_ai 胜率最高 → 槽 1
- 哪个对最新主模型胜率 ~50% → 槽 2
- 哪个对最新主模型胜率最低（即克制主模型） → 槽 3

## 5. 召唤师技能学习升级（A 类）

### 5.1 现状问题

- 训练时 cycle 模式：每个对位 (my_hero, opp_hero) 循环 `[80110, 80115, 80102]`，4 种对位 × 3 技能 = 12 个组合都跑
- eval 时**固定走 80110**（`_default_summoner_skill`）→ 模型学了一堆数据但 eval 用不上

### 5.2 改造方案：胜率 EMA 表 + ε-greedy

加一个 12-cell 的 EMA 胜率表，按对位 + 技能持久化：

```python
# 新增文件 agent_diy/conf/summoner_winrate.json，每对位 + 技能维护 EMA
{
    "112-112": {"80110": 0.52, "80115": 0.61, "80102": 0.48},
    "112-133": {"80110": 0.55, "80115": 0.49, "80102": 0.58},
    "133-112": {...},
    "133-133": {...}
}
```

在 `agent.py:_select_train_summoner_skill` 改为：

```python
def _select_train_summoner_skill(self, my_hero, opponent_hero):
    candidates = list(GameConfig.SUMMONER_SKILL_CANDIDATES_BY_HERO.get(my_hero, []))
    # ε-greedy: 80% 走当前 EMA 最高，20% 探索
    table = self._load_winrate_table()
    key = f"{my_hero}-{opponent_hero}"
    if random.random() < 0.2 or key not in table:
        return random.choice(candidates)
    return max(candidates, key=lambda s: table[key].get(str(s), 0.5))

# 每局结束在 agent.learn 之外、workflow 层做：
def on_episode_end(self, my_hero, opp_hero, skill, win):
    key = f"{my_hero}-{opp_hero}"
    table = self._load_winrate_table()
    table.setdefault(key, {})
    old = table[key].get(str(skill), 0.5)
    table[key][str(skill)] = 0.95 * old + 0.05 * win
    self._save_winrate_table(table)
```

### 5.3 eval 时也用学到的表

```python
def _default_summoner_skill(self, my_hero, opponent_hero):
    table = self._load_winrate_table()
    key = f"{my_hero}-{opponent_hero}"
    if key in table and table[key]:
        return int(max(table[key], key=table[key].get))
    return GameConfig.DEFAULT_SUMMONER_SKILL
```

**为什么用 EMA 不用 REINFORCE**：12 个组合 × 训练几百局后才有统计意义，REINFORCE 会因方差太大反复抖动；EMA + ε-greedy 是工程上更稳的简化。

### 6.1 必须监控的字段（已在代码中就位）

| 字段 | 来源 | 健康范围（v2 MID 阶段） |
|---|---|---|
| `reward_sum` | workflow | 单调上升 |
| `reward_<key>`（12 个） | workflow | 各项不应有持续 reward 主导（如 forward 占 >40% 是 hack） |
| `win_rate`（vs common_ai / vs each model_id） | env | LATE 阶段对 common_ai >85%，对 pinned 强 ckpt 50±5% |
| `tower_hp`、`kill`、`death`、`frame` | env | 胜局帧数下降、kill/death > 1.5 |
| `mean_ratio`、`approx_kl`、`clip_fraction` | algorithm | ratio ≈ 1.0、KL < 0.15、clip_fraction < 0.2 |
| `value_loss`、`policy_loss`、`entropy_loss` | algorithm | value 平滑下降、entropy 不跌穿 0.5 |
| `action_<X>_count`（noop/move/attack/skill/recover/recall）| workflow | noop < 5%、attack+skill > 30% |
| `selected_summoner_<id>` | workflow | 各 hero 对位上分布应该收敛（非均匀）|

### 6.2 红线告警

- `value_loss` 单 10 分钟内跳 5x → 阶段切换太激进，立刻回滚 lr
- `entropy_loss` 跌穿 0.001 → 策略坍缩，提高 BETA_END 到 0.005 重训
- `mean_ratio` 持续 > 1.5 或 < 0.7 → ratio 失控，把 `model_file_sync_per_minutes` 调密
- `kill_cnt` 持续为 0、`hurt_to_hero` 持续为 0 → reward hacking 嫌疑（farming 项过大），降 money/exp 权重

## 7. 落地优先级（建议执行顺序）

按 v2 之后的 v3 / v3.1 / v3.2 三个小版本拆分（全是 A/B 类，可在 v2 ckpt 上热启动 + warmup）：

### v3.0（B 类 warmup，2-3h 启动期）
1. 改 3 个权重数值（§2.1）：kill +0.8、forward 0.05、cake_pickup 0.3
2. cake_pickup 判定从 `hp_rate >= 1.0` 收紧到 `hp_rate >= 0.9`（§2.1 配套改动）
3. 重写时间衰减（§2.3）：per-key 衰减，KDA/tower 不衰减，forward 保持现有 1000 帧硬截断
4. 加 `return running std`（§2.5，A 类）
5. **加终局胜负 reward**（§2.6.1）：win=+5.0 / lose=-5.0

预期：训练曲线更平滑，KDA 相关 reward 占比上升 5-10%，终局信号反传增强；胜率短暂下跌 5% 后超过 v2。

### v3.1（A 类 + B 类 warmup 混合）
6. 半 PFSP 对手采样（§4.2，A）
7. `kaiwu.json` 三槽重新分配（§4.3，A）：需要先做一次三模型互测
8. 召唤师技能 EMA 表（§5，A）
9. **情景化权重衰减**（§2.6.2，B）：残血 / 敌方残血 / 终局推塔等 4 触发
10. **镜像数据增强**（§2.6.4，A）：sample_process 加 mirror augmentation + 单元测试
11. PBRS forward 改造（§2.6.3，A，选做）

预期：对 pinned 强 ckpt 胜率从 50% 提升到 55-60%，对 common_ai 胜率不降；critic 收敛更快。

### v3.2（B 类 warmup）
12. 三段式权重调度（§3.1）：实现 EARLY/MID/LATE 切换
13. γ/λ/entropy 课程（§3.2）
14. 切换信号监控（§3.3）

预期：进入 LATE 后击杀效率提升、平均胜局帧数下降 10-20%。

### v3.3+（用户主导 + 二级备选）
15. 录像分析 + 失败模式定向情景奖励（user 自行迭代）
16. `no_op_streak_penalty` 等通用情景项（§2.2）按需开启
17. SIL 自模仿学习（§2.6.5，选做）：仅当对手池退化无法用 PFSP 解决时再上
