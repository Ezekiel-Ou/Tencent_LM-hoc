# 腾讯“开悟”强化学习项目系统化调研报告

> 面向对象：腾讯开悟 hok1v1 强化学习项目技术团队  
> 主要依据：本地官方开发指南、本地初步调研报告、当前代码包、`kaiwu_taichu/hok_semi` 外部仓库、知乎技术文章、arXiv 论文  
> 说明：本报告优先遵循项目文档和本地初步调研结论；外部资料用于补充方法论、实现策略和风险判断。

## 1. 引言与背景

腾讯“开悟”强化学习项目提供标准化的强化学习开发框架，核心目标是让智能体在复杂交互环境中通过环境观测、动作选择、样本构造、策略更新和模型评估形成闭环训练。本项目对应的 hok1v1 任务是王者荣耀墨家机关道 1v1：红蓝双方各控制一名英雄，在 20000 帧上限内以摧毁对方防御塔作为胜负目标。

从任务本质看，hok1v1 属于长时序、部分可观测、层次化动作空间、奖励稀疏与稠密信号混合的复杂决策问题。智能体需要同时处理走位、补刀、技能释放、目标选择、塔血推进、血量风险、经济经验发育和对手建模。因此，项目的核心不是“换一个新算法”，而是围绕 PPO 框架补齐特征、奖励、网络结构、样本处理、自对弈课程和评估监控。

本次调研采用四类信息源：

- 本地项目文档：明确接口、协议、动作空间、训练流程、评估模式和平台限制。
- 本地初步调研报告：总结当前 baseline 的结构缺口、已知 bug、优化路线和竞赛经验。
- 外部仓库 `wty-yy/kaiwu_taichu/hok_semi`：参考更完整的状态建模、网络结构、奖励与监控实现。
- 外部文章与论文：归纳多智能体强化学习、MOBA 决策、PPO 稳定性、奖励尺度鲁棒性等方法论。

## 2. 项目文档与初步调研总结

### 2.1 任务与环境约束

| 维度 | 项目约束 | 技术含义 |
| --- | --- | --- |
| 对局形式 | 王者荣耀墨家机关道 1v1 | 单智能体对抗为主，但训练可使用 self-play 和历史模型池 |
| 可控英雄 | 鲁班七号 112、狄仁杰 133 | 英雄池小，适合做英雄特化特征和召唤师技能策略 |
| 胜负目标 | 摧毁敌方防御塔 | 奖励设计必须围绕推塔目标，而不是只优化击杀 |
| 时间尺度 | 1 step = 6 frame，1 frame 约 33ms | 决策频率约 5Hz，需要时序模型捕捉技能 CD、压塔窗口和撤退节奏 |
| 终止条件 | 防御塔被摧毁、20000 帧超时、异常 | 超时双方不得分，应设计推进压力和时间衰减 |
| 评估方式 | 多轮循环累计胜场 | 需要泛化到 112/133 双英雄和红蓝双方镜像场景 |

### 2.2 开发框架约定

官方框架将强化学习项目拆分为 `agent`、`feature`、`model`、`algorithm`、`workflow` 和 `conf` 等模块：

- `agent.py`：承载 `predict`、`exploit`、`learn`、`load_model`、`save_model`、`init_config` 等接口。
- `feature/definition.py`：定义 `ObsData`、`ActData`、`SampleData`，负责观测处理、动作处理、样本构造和 GAE。
- `feature/reward_process.py`：实现奖励子项、零和奖励和帧间差分。
- `model/model.py`：实现 PyTorch 策略价值网络。
- `algorithm/algorithm.py`：消费样本并执行 PPO 更新。
- `workflow/train_workflow.py`：管理环境交互、阵容轮换、评估、对手加载、采样和模型保存。

这一分层对后续生成 `AGENTS.md` 和任务计划很重要：技术任务应按模块切分，优先保证接口兼容，再局部增强特征、奖励、模型和自对弈流程。

### 2.3 动作与观测协议

hok1v1 使用层次化离散动作空间，PPO baseline 中动作维度为：

```text
LABEL_SIZE_LIST = [12, 16, 16, 16, 16, 9]
```

含义分别是：

| Head | 维度 | 含义 |
| --- | ---: | --- |
| button | 12 | 不动作、移动、普攻、技能、治疗、召唤师技能、回城、装备技能等 |
| move_x | 16 | 移动方向 X |
| move_z | 16 | 移动方向 Z |
| skill_x | 16 | 技能方向 X |
| skill_z | 16 | 技能方向 Z |
| target | 9 | 空目标、敌方英雄、自身、防御塔、4 个小兵、1 个野怪 |

环境同时提供 `legal_action` 和 `sub_action_mask`。这意味着策略网络不能只输出 logits，还必须在采样和 loss 计算中严格应用合法动作掩码，尤其要处理 `button -> target/方向` 的条件依赖。

### 2.4 当前 baseline 的主要缺口

本地初步调研和代码核对显示，`agent_ppo` 是可运行但能力上限很低的骨架：

| 问题 | 当前状态 | 影响 |
| --- | --- | --- |
| 特征维度过低 | `DIM_OF_FEATURE = [10]` | 只覆盖极少数英雄/塔信息，看不到完整对线局面 |
| 奖励项过少 | 仅 `tower_hp_point` 和 `forward` | 学不到血量、击杀、死亡、经济、经验、补刀等关键行为 |
| LSTM 未真正接入 forward | 初始化了 LSTM，但 forward 只走 MLP | 时序状态形同虚设，无法建模 CD、连招和风险窗口 |
| Target attention 未使用 | 声明了 target embedding 层但未参与计算 | 目标选择退化为普通分类，难以稳定处理多单位交互 |
| value loss 覆盖 | `value_cost` 被重复赋值 | 价值学习目标不清晰，可能影响 critic 稳定性 |
| dual-clip 实现不标准 | 对 ratio 无条件 clamp 到 `[0, 3]` | 与绝悟 dual-clip PPO 的负优势分支约束不一致 |
| 召唤师技能随机选择 | `init_config` 随机选 1 个技能 | 丢失对阵策略入口，评估波动大 |

baseline 中也有应保留的部分：

- 阵容轮转已经覆盖鲁班/狄仁杰和红蓝双方组合。
- 样本构造已按 `LSTM_TIME_STEPS=16` 组织，具备接入时序模型的基础。
- GAE 计算和帧间差分奖励框架已存在。
- `target_legal_action * one_hot_button` 的条件 mask 思路正确。
- workflow 已预留 `common_ai`、`selfplay`、自定义模型 ID 对手加载路径。

## 3. 外部仓库分析：`kaiwu_taichu/hok_semi`

`wty-yy/kaiwu_taichu` 的 `2025/hok_semi` 分支是一个面向开悟半决赛环境的强化学习项目实现，README 显示其提供了可提交版本、提交结果、半决赛报告和演示视频。虽然该仓库的英雄和部分环境配置与当前 hok1v1 不完全一致，但其工程设计对本项目具有较高参考价值。

### 3.1 模块结构

外部仓库保留了开悟标准代码包分层：

| 模块 | 作用 | 可借鉴点 |
| --- | --- | --- |
| `agent_ppo/conf` | 维度、动作、奖励、超参配置 | 将状态维度、网络维度和奖励权重显式配置化 |
| `agent_ppo/feature` | 状态构建、奖励管理、监控数据构建 | 将观测构造成结构化状态，而非极低维手工特征 |
| `agent_ppo/model` | PPO 策略价值网络 | 使用位置编码、单位编码、LSTM/MLP 融合和目标注意力 |
| `agent_ppo/workflow` | 训练主循环 | 支持多阶段训练和指标上报 |
| `conf` | 平台运行配置 | 与开悟标准入口保持一致，便于提交 |

### 3.2 状态建模亮点

外部仓库 README 中明确将状态划分为离散状态和连续状态，总维度约 3910。其设计强调：

- 共享位置编码：将实体位置统一映射到网格或离散编码，减少坐标尺度带来的学习难度。
- 英雄、塔、小兵、技能、buff 等单位状态分组建模。
- 同时保留离散身份信息和连续数值信息。
- 针对自身、敌方、单位、目标对象做不同编码，再在网络中融合。

对本项目的启示是：特征工程应从 10 维 baseline 扩展为“多组结构化特征”，至少覆盖双英雄状态、技能 CD、召唤师技能、塔血、小兵、经济经验、位置、可见性、伤害事件和全局时间。

### 3.3 网络结构亮点

外部仓库说明其 v2.0 结构采用：

- 前处理 embedding；
- LSTM 状态分支；
- MLP 当前帧分支；
- 融合层；
- 策略 head、价值 head、目标注意力；
- Value normalization。

这与绝悟论文中的核心思想一致：MOBA 决策不是单一 flat feature 分类问题，而是“当前态势 + 历史状态 + 目标选择 + 多头动作”的组合建模问题。

可迁移到本项目的结构原则：

- 先按单位类型编码，再做全局融合。
- 时序层只承载必要记忆，不宜在小算力下盲目堆大 LSTM。
- target head 应基于候选目标 embedding 和主干 hidden state 做 attention。
- 多动作 head 分别输出，并在 loss 中按合法动作和强化学习任务标记加权。

### 3.4 奖励与监控亮点

外部仓库的 README 与代码描述包含 8 项奖励权重，与开悟/MOBA 任务常见设计一致：

| 奖励方向 | 作用 |
| --- | --- |
| 塔血 | 对齐最终胜负目标 |
| 英雄血量 | 约束换血收益 |
| 法力/能量 | 防止无效消耗 |
| 击杀/死亡 | 学习强对抗行为和避险 |
| 经济/经验 | 支持补刀和发育 |
| 补刀 | 提高资源获取效率 |
| 前进/推进 | 减少保守停滞 |

外部仓库还强调监控模块，包括 reward、tower hp、K/D、伤害、loss 等指标。对本项目而言，监控不是附属功能，而是发现 reward hacking、自对弈退化、策略熵坍塌和训练不稳定的必要工具。

### 3.5 与本项目差异及适配策略

`kaiwu_taichu/hok_semi` 可以作为我们的高分基线来源，但它对应的是 2025 半决赛版本；当前项目是官方 hok1v1 鲁班/狄仁杰赛题。建议将其主体工程改写到 `agent_diy`，先做协议和英雄适配，再在适配版上继续优化。

| 维度 | `kaiwu_taichu/hok_semi` | 本地 hok1v1 | 适配动作 |
| --- | --- | --- | --- |
| 英雄池 | 后羿 `169`、李元芳 `173`、虞姬 `174` | 鲁班七号 `112`、狄仁杰 `133` | 删除旧英雄分支，重写 112/133 技能、buff、被动、CD 特征 |
| 阵容轮换 | 三英雄组合 | 两英雄红蓝轮转 | 改为 `[112, 133]` round-robin |
| 状态维度 | README 描述约 `3910` 维，离散/连续拆分 | baseline 当前 10 维，最终维度由我们重算 | 保留结构化 schema 思想，重新计算所有 split shape |
| 英雄专属状态 | 后羿/李元芳/虞姬 mark、技能状态 | 鲁班扫射被动、狄仁杰被动层数/控制解除/大招眩晕等 | 重写 hero-specific extractor |
| 地图实体 | 英雄、小兵、塔、河蟹、飞行物、血包等 | 文档明确英雄、小兵、塔；协议包含 monster、bullets、cakes | 保留通用实体框架，不稳定实体置零并保留 mask |
| 召唤师技能 | 需按其半决赛策略核对 | 本赛题开放 10 个召唤师技能，`init_config` 赛前选择 | 改为 112/133 对阵规则或可学习表 |
| 动作空间 | 层次化动作，预期与开悟 1v1 接近 | `[12,16,16,16,16,9]` | 保留多 head 结构，强校验 target 顺序 |
| reward | 多项 reward 管理 | 需要塔血、血量、击杀、死亡、经济、经验、补刀、forward | 复用 reward manager 结构，重设权重和字段来源 |
| 模型结构 | encoder + MLP/LSTM + target attention + value norm | 官方 baseline 仅 MLP，LSTM/attention 未实际接入 | 作为初始高分基线结构保留，先简化到可跑通 |
| workflow | 半决赛配置和模型池逻辑 | 本地官方 `common_ai/selfplay/model_id` | 对齐本地 `train_env_conf.toml` 和 `kaiwu.json` |

结论：后续开发可以先把 `hok_semi` 改造成符合本赛题的 `agent_diy` 基线，再在该基线之上进行 PPO 稳定性、特征、奖励、自对弈和提交策略优化。

## 4. 文献与文章技术总结

### 4.1 MOBA 强化学习：PPO、动作解耦与目标注意力

绝悟 AAAI 2020 论文《Mastering Complex Control in MOBA Games with Deep Reinforcement Learning》将 1v1 MOBA 控制问题抽象为复杂动作空间下的深度强化学习问题，关键技术包括：

- 使用 PPO 作为主算法；
- 引入 dual-clip PPO 提升带噪声优势估计下的稳定性；
- 对动作空间做多 head 解耦，分别建模按键、方向和目标；
- 使用 action mask 保证非法动作不参与采样；
- 使用 LSTM 捕捉部分可观测环境中的历史信息；
- 对目标选择使用 attention，让策略根据当前 hidden state 选择交互对象。

这与本项目现状高度一致：当前 baseline 已经有多 head 和 mask 的雏形，但缺少完整特征、时序接入和目标注意力，是最优先的技术补齐方向。

### 4.2 Honor of Kings Arena 环境经验

NeurIPS 2022 的 Honor of Kings Arena 论文强调，MOBA 环境用于检验泛化能力和复杂控制能力，1v1/3v3/5v5 都需要处理：

- 大状态空间；
- 层次化动作；
- 不同英雄机制；
- 规则 AI、自对弈、历史模型等不同对手；
- 胜率、Elo、对局时长等综合指标。

对本项目而言，评价指标不能只看训练 reward。至少应同时看：

- `win_rate`；
- 自/敌塔血；
- 对局总帧数；
- `money_per_frame`；
- kill/death；
- `hurt_to_hero` / `hurt_by_hero`；
- entropy、policy loss、value loss、KL 或 ratio 分布。

### 4.3 知乎技术文章总结

用户指定的知乎文章中，`p/657946316` 可直接访问，其主题是“腾讯多智能体强化学习大赛奖励函数专题（二）”。该文强调：

- 奖励函数常依赖大量调试和人工经验；
- 奖励设计应服务于可解释的行为目标；
- 不同阶段的训练目标可能需要不同奖励侧重；
- 可通过限制或引导动作行为来缩小策略搜索空间；
- 工程可用性通常比公式复杂度更重要。

其余指定知乎链接在本次工具访问中存在 403/robots 限制，因此本报告不直接引用其正文细节，而采用本地初步调研报告中已经提炼的结论：

- PPO 是开悟 MOBA 任务中的主线算法选择，竞赛差异主要来自网络、奖励、loss 和 self-play 课程；
- 动作约束损失可以抑制站桩、无效回城、乱放技能等行为；
- 情景奖励可放大稀有但关键的战术样本；
- 自对弈不能只用 naive self-play，应维护历史模型池并引入按弱点采样的课程机制；
- 小算力场景下不宜盲目堆大模型，FC/GRU 或 MLP/LSTM 混合结构可能比纯大 LSTM 更稳。

### 4.4 arXiv:2310.17805 对 PPO 稳定性的启示

arXiv:2310.17805《Investigating the properties of neural network representations in Reinforcement Learning》围绕 PPO 与 DreamerV3 风格技巧在不同任务中的表现进行分析，重点提醒我们：

- 奖励尺度、归一化、裁剪和 value 目标会显著影响 PPO 表现；
- 某些在世界模型或特定 benchmark 中有效的技巧，不一定能直接迁移到 PPO；
- 对 PPO 来说，value normalization、symlog、two-hot critic 等技巧需要实验验证，而不是默认采用；
- 稳定性改进必须结合环境奖励分布和网络结构一起评估。

对本项目的直接启示是：可以尝试 value normalization、reward clipping、advantage normalization 和 PopArt 类思想，但必须以胜率、塔血、对局时长和策略熵为准绳，不应只因为外部论文有效就无条件接入。

## 5. 技术对比与启示

### 5.1 方法对比

| 方法 | 优点 | 风险 | 适用建议 |
| --- | --- | --- | --- |
| 原始 PPO baseline | 接口完整、易跑通、与平台兼容 | 特征/奖励/网络过弱 | 作为工程骨架，不作为最终策略能力来源 |
| Dual-clip PPO | 对负优势样本更稳，适合 MOBA 噪声优势估计 | 实现细节易错 | 应替换当前伪 dual-clip |
| 大维 LSTM | 理论上增强长时记忆 | 小算力下易过拟合、训练慢 | 优先接入轻量 GRU/LSTM 或混合分支 |
| Target attention | 适合多目标动作选择 | 需要候选目标 embedding 和 mask 对齐 | 强烈建议实现 |
| 稠密奖励 shaping | 学习信号充分 | 容易 reward hacking | 必须配合监控和回放分析 |
| 情景奖励 | 放大关键稀有样本 | 数值过大可能破坏 value 学习 | 作为中后期增强，不宜首版堆太多 |
| Naive self-play | 简单、平台支持 | 容易策略退化或自我过拟合 | 仅作过渡 |
| PFSP/历史模型池 | 提高鲁棒性和补短板能力 | 需要胜率统计和模型池管理 | 中后期应接入 |
| Value normalization / PopArt | 降低奖励尺度敏感性 | 实现复杂，可能不稳定 | 小步 A/B 测试 |

### 5.2 可借鉴设计原则

1. **先对齐项目协议，再增强算法**  
   所有改动必须保持 `ObsData`、`ActData`、`SampleData`、`predict`、`exploit`、`learn`、`workflow` 与平台接口兼容。

2. **PPO 是主线，工程质量决定上限**  
   当前阶段不建议转向 SAC、Rainbow、MuZero 等高成本路线。投入重点应是 dual-clip PPO、advantage normalization、value loss 修正和合法动作处理。

3. **特征工程优先级最高**  
   当前 10 维特征无法支撑复杂决策。首要目标是构建结构化多组特征：双英雄、小兵、防御塔、技能、召唤师技能、经济经验、伤害事件、可见性、时间与地图位置。

4. **奖励必须围绕推塔胜负闭环**  
   击杀、经济和伤害只是手段；塔血和推进效率必须保持最高优先级。奖励项应使用零和差分，避免双方都保守刷分。

5. **目标选择要显式建模**  
   目标不是普通动作类别，而是与敌方英雄、小兵、塔、野怪等候选实体相关。target attention 比 flat target head 更符合任务结构。

6. **自对弈需要课程设计**  
   先用 common_ai 学基础，再切 self-play，最后用历史模型池和 PFSP 补短板。评估时保留 common_ai 和多个历史 checkpoint，防止只适配自身风格。

7. **监控指标要服务于诊断**  
   reward 上升不等于策略变强。必须同步观察胜率、塔血、K/D、伤害、经济、对局帧数、entropy、value loss 和 PPO ratio。

### 5.3 旧调研报告高价值迁移

旧版 `调研报告.md` 不再作为后续开发主文档，但其中部分实战策略仍有工程价值，建议作为战术备忘录纳入后续计划。

| 主题 | 可迁移内容 | 使用边界 |
| --- | --- | --- |
| 动作约束损失 | 对 `button=NONE`、满血回城、满血治疗、明显无效技能等行为，在 policy loss 外增加软约束 | 作为可配置辅助 loss，不替代合法动作 mask；必须监控动作分布，避免压制必要等待动作 |
| 情景奖励 | 对塔下命中、关键技能命中、残血错误进攻、连续空动作、错失推塔窗口等稀有样本放大奖励 | 中后期再接入；每个情景必须有触发计数和 reward 分项监控 |
| 小算力网络设计 | 采用 MLP/FC 当前帧分支 + GRU/LSTM 时序分支的混合结构，避免纯大 LSTM 过拟合 | 先完成最小可用 LSTM/GRU，再做 FC:GRU 比例实验 |
| 课程式奖励 | 早期偏发育和推线，中期平衡，后期提高击杀、压塔和终局奖励 | 需要平滑切换，避免 reward 权重突变导致策略退化 |
| Self-play 评分机制 | 维护历史模型池，并按胜率弱点采样；对难打历史模型提高采样概率 | 先跑通 common_ai 和 latest self-play，再实现 PFSP |
| Module Soup | 对多个风格互补 checkpoint 做 state_dict 加权平均 | 仅作为后期提交策略；前提是网络结构完全一致，且融合后必须重新评估 |
| 代码审计 checklist | 检查镜像变换、feature/head 对齐、SAMPLE_DIM、两个 agent 模型加载、mask 与动作 head 对齐 | 每次大改 feature/model/loss 后必须执行 |

这些内容的定位是“增强项”，不是第一阶段开发阻塞项。第一阶段仍以官方接口兼容、baseline bug 修复、结构化特征和基础 8 项奖励为核心。

## 6. 结论与建议

本项目的最短有效路径是：以当前 `agent_ppo` 作为可运行工程骨架，吸收 `kaiwu_taichu/hok_semi` 和绝悟体系中的结构化设计，把“特征、奖励、模型、loss、自对弈、监控”六个模块补齐，而不是重写一套算法框架。

可直接应用的技术结论如下：

- 算法主线固定为 PPO，并修正为标准 dual-clip PPO。
- 扩展奖励项到塔血、血量、击杀、死亡、经济、经验、补刀、推进等组合，并保持零和差分。
- 将 LSTM/GRU 真正接入 forward，避免当前“样本有时序、模型不用时序”的断裂。
- 实现 target attention，并与合法动作 mask 和 `sub_action_mask` 保持一致。
- 将 10 维观测升级为结构化多组特征，首版不追求一步到位，但必须覆盖敌方英雄、技能 CD、塔血、小兵和经济经验。
- 将召唤师技能从随机选择改为对阵条件策略，至少按英雄组合给出规则策略，后续再学习化。
- 自对弈从 common_ai 预热、latest self-play、历史模型池、PFSP 分阶段推进。
- 对 reward normalization、PopArt、value clipping 等稳定化 trick 做小规模验证，避免盲目叠加。

面向后续 `AGENTS.md` 和任务 plan，建议将工作拆成以下模块职责：

| 模块 | 后续任务方向 |
| --- | --- |
| Feature Agent | 扩展观测、归一化、镜像处理、候选目标 embedding |
| Reward Agent | 扩展奖励子项、零和差分、情景奖励、reward 日志 |
| Model Agent | 接入 LSTM/GRU、target attention、多 head 输出、value head |
| Algorithm Agent | 修 dual-clip、advantage normalization、value clipping、loss 监控 |
| Workflow Agent | common_ai 预热、自对弈、历史模型池、PFSP、评估配置 |
| Evaluation Agent | 指标面板、对局回放诊断、模型池对战矩阵、提交候选筛选 |
