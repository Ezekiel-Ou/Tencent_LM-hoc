# v2.1 改动清单：狄仁杰 2 技能时机硬约束

> 产出日期：2026-05-16
> 适用前提：v1.2 锚定的特征/网络/LSTM 等结构性维度全部 **冻结**；本文只记录小步的规则层/legal_action 层硬约束改动，不动 reward 项数量、不动网络。
> 背景：v1.2 已经把 `cleanse_success` (weight 0.15) 和 `_compute_cleanse_events` 里的 "skill2 misuse" 软惩罚 (`reward_process.py:603-605`) 都上线了，但实际训练中仍观察到狄仁杰 2 技能存在**显著"乱放"现象**——窗口外、远离敌人时仍会施放，浪费 CD 与净化机会。

---

## 0. 执行摘要（TL;DR）

| 项 | 现状 | 本次改动 | 续训类别 |
|---|---|---|---|
| 狄仁杰 2 技能时机 | 仅有"该放时强制放"的正向规则 `_maybe_auto_cleanse` + 软惩罚 misuse | 在 133v133 镜像对局加 **反向硬 mask**：满足条件时把 button=5(技能2) 的 legal 位置零 | A（不改 reward 项数 / 不改网络，仅 legal_action 改） |
| `cleanse_success` 公式 | `cleanse_main - cleanse_enemy - skill2_misuse`，含敌方净化我方大招的零和惩罚项 | 删除 `- cleanse_enemy` 项，改为 `cleanse_main - skill2_misuse`；`cleanse_enemy` 保留为 monitor-only | A（仅 reward 公式改） |
| 狂暴 (80110) 释放后无输出惩罚 | 仅有"释放后 20 帧内未进入 7000 范围 → −0.8"的位置判定 | 新增 **`berserk_no_damage_penalty`**：释放后 **60 帧** 内未对敌方小兵/英雄/防御塔造成任何伤害 → −1.5，与现有 `berserk_timing` 并行扣 | A（新增 1 项 reward，不改网络） |
| 狄仁杰大招命中后续追打 | `direnjie_skill3_followup_damage = 0.10`，每次大招命中**只能领一次** +1.0 事件 | 改为 **每帧独立计数**：30 帧窗口内，每帧若我方对敌方英雄造成伤害则记 +1.0，**单次大招命中最多累计 8 次**；权重保持 0.10 | A（reward 检测逻辑改 + 状态字段改，权重不动） |

## 1. 现状回顾

### 1.1 已有的正向规则（保留，不动）

`agent_diy/agent.py:371-404` 的 `_maybe_auto_cleanse`：
- 仅在 `main_config_id == 133 and enemy_config_id == 133` 时启用 (`377`)。
- 检测 `take_hurt_infos` 中 `attacker = 敌方 runtime` 且 `skill_slot == 3`，即己方被敌方大招命中 (`383-388`)。
- 2 技能可用且 CD≤0 时强制覆盖动作为 `[5, 15, 15, 15, 15, 2]`，并累计 `cleanse_override_count` (`393-404`)。
- 同时挂在 `predict` (`247`) 和 `exploit` (`258`) 两条路径上，采样/评估一致。

### 1.2 已有的软惩罚（保留，不动）

`agent_diy/feature/reward_process.py:603-605` 的 `_compute_cleanse_events`：
- 仅在双方都是 133 时计算；
- `main_used_skill2 and not _is_in_berserk_engagement → _skill2_misuse_count += 1`；
- 通过 `cleanse_success` 项 (weight 0.15) 以 `cleanse_main - cleanse_enemy - skill2_misuse` 的形式参与训练。

### 1.3 现存问题

1. **正向规则只保证"该放时不漏放"**：覆盖只发生在被命中后那一帧 + 后续条件满足时，**不约束**其他帧的随机施放。
2. **软惩罚不够强**：`cleanse_success` 权重 0.15，单次 misuse 仅 −0.15；模型在探索阶段权衡"省一个 CD 的代价"时几乎察觉不到，"乱放"无法收敛到零。
3. **engagement 判据过宽**：`_is_in_berserk_engagement` 仅看"敌存活 + 距离 ≤ 7000"，与"是否真的需要净化"高度解耦——敌方在 6500 处但没有放大招，照样算"在交战"，misuse 不触发。

## 2. 本次改动：在 legal_action 层加反向硬 mask

### 2.1 规则原文（用户给定）

> 在狄仁杰打狄仁杰的对局中，**如果对方英雄没有死亡** 且 **敌方英雄等级 > 4** 且 **近 300 帧内未使用过大招**，则不允许我方狄仁杰使用二技能，确保我方狄仁杰的二技能留给最重要的时候。

### 2.2 触发条件（合取，全部满足才 mask）

| 条件 | 实现位置 | 备注 |
|---|---|---|
| `main_config_id == 133` | hero state 的 `config_id` | 镜像门控的本侧 |
| `enemy_config_id == 133` | 同上 | 镜像门控的对方；非镜像不改 |
| `enemy_hp > 0` | enemy hero `hp` | "对方英雄没有死亡" |
| `enemy_level >= 4` | enemy hero `level` | 大招 4 级解锁，等敌方有大招才约束 |
| `frame_no - _enemy_ult_cast_frame > 300` 或 `_enemy_ult_cast_frame is None` | 新增跟踪 `_enemy_ult_cast_frame`（见 §2.3） | "近 300 帧内未使用过大招" |

> 上述任一不满足，则**不 mask**，2 技能正常进入 legal_action；满足全部，则**强制 mask**，模型当帧无法采样到 skill 2。

### 2.3 "近 300 帧内未使用过大招" 的判定（写死）

依据 `开发指南/数据协议.md:230`，`succUsedInFrame` 字段的官方定义是：

> `succUsedInFrame | int32 | 当前帧成功使用次数`

也就是 **当帧成功释放次数**——只有"该帧成功施放"的那一帧 > 0，下一帧自动归 0。**这是单帧边沿信号，不是持久帧号**。

因此实现写死如下：

1. **新增状态**：在 `Agent.__init__` / `reset` 里加一个实例字段 `self._enemy_ult_cast_frame = None`。
2. **每帧采样前更新**（放在 `predict` / `exploit` 进入推理前，与 `_maybe_block_skill2` 同一调用位置的上游）：

    ```text
    enemy_hero = <find by camp>
    enemy_slot3 = <slot in enemy_hero.skill_state.slot_states whose slot_type == 3>
    if enemy_slot3 is not None and float(enemy_slot3.succUsedInFrame or 0) > 0:
        self._enemy_ult_cast_frame = current_frame_no
    ```

    即：观察到敌方 slot 3 当帧 `succUsedInFrame > 0` 的边沿，就把当前 `frame_no` 写入 `_enemy_ult_cast_frame`。该字段一直保留上一次的施放帧号，不会因为下一帧归 0 而被覆盖。

3. **mask 判定**：

    ```text
    last = self._enemy_ult_cast_frame
    enemy_ult_inactive = (last is None) or (current_frame_no - last > 300)
    ```

    `enemy_ult_inactive == True` 即"近 300 帧内未使用过大招"，与 §2.2 其他四条合取后触发 mask。

4. **新局重置**：在 `reset(observation)` 里把 `_enemy_ult_cast_frame` 重置为 `None`，与现有的 `force_home_phase` / `rule_override_active` 重置位 (`agent.py:111-122`、`agent.py:181-193`) 写在同一处。

> 注意区别：现有的 `_main_ult_hit_frame` / `_enemy_ult_hit_frame` (`reward_process.py:580-587`) 跟踪的是**命中帧**（来自 `take_hurt_infos`，attacker = 对方 runtime + slot=3），命中比施放滞后 0.5–2 秒。本文用的 **施放帧** 严格贴近用户规则文字"未使用过大招"，且飞行途中也算作"已使用"——避免在敌方刚抬手未命中时仍允许我方 2 技能、错过预判净化的窗口。两套帧号互不影响、可并存。

### 2.5 实现位点（落地阶段决定，本文不动代码）

候选 1：在 `feature_process.py` 生成 `legal_action` 数组时统一加。优点：采样和推理两条路径自动一致；缺点：要找到生成 legal_action 的具体函数，可能涉及对 action head 5（skill 选择）的 mask 维度。

候选 2：在 `agent.py` 的 `predict` / `exploit` 里仿照 `_maybe_auto_cleanse` 的做法，在 `action_process` 之前调用一个 `_maybe_block_skill2` hook，在 `legal_action` 副本上把对应位置 0 后再走推理。优点：改动局部、易回滚；缺点：必须同时挂两条路径，与现有 `_maybe_auto_cleanse` 同位置即可。

倾向 **候选 2**：与 `_maybe_auto_cleanse` 风格一致、回滚成本最低；落地时把 `_maybe_block_skill2` 放在 `_maybe_auto_cleanse` 之前调用（先 mask、再决定是否被正向规则覆盖；理论上两者不会同时触发：正向规则要求"被命中"，反向规则要求"近 300 帧未释放"——若刚被命中，敌方一定刚释放过，反向条件不满足，mask 自动不生效）。

### 2.6 删除"敌方 2 技能净化我方大招"的零和惩罚项

本次同步移除 `cleanse_success` 项中的 `-_cleanse_enemy_count` 部分，即 `reward_process.py:208` 当前的：

```python
reward_struct.cur_frame_value = float(
    self._cleanse_main_count - self._cleanse_enemy_count - self._skill2_misuse_count
)
```

改为：

```python
reward_struct.cur_frame_value = float(
    self._cleanse_main_count - self._skill2_misuse_count
)
```

理由：
1. **不是乱放主因**：该项只在镜像对局触发，惩罚的是"我方大招被敌方净化"，与我方"乱放 2 技能"是两件事。
2. **信号噪声**：被敌方净化本质是对方的合理操作，惩罚我方会让我方学到"不敢开大招"的副作用——尤其在 mask 反向硬约束生效后，我方 2 技能保留率提高，理论上敌方净化我方大招的频率也会上升，零和项会变成持续抑制开大的负梯度。
3. **保留对称性的需求消失**：上一版保留该项是因为镜像 critic 对称；但 mask 让镜像策略本身已经强对称（双方都只能在被打大招后放 2），critic 不再需要靠 reward 对称项来稳定。
4. **`_cleanse_enemy_count` 计算逻辑保留**：仅在 reward 求和处剔除该项，便于将来观察"敌方净化我方"频次，作为监控指标导出而非梯度信号。

同步动作（落地时一并改）：
- `reward_process.py:208` 公式按上面写法改；
- 把 `_cleanse_enemy_count` 作为 monitor 指标 (`reward_enemy_cleansed_us`) 导出，权重 0、仅做日志。

### 2.7 关于"等级 >= 4" 的解释

用户规则原文写的是"大于 4"，本文按其后续澄清取 **`>=4`**——即敌方大招解锁的那一刻就开始约束我方 2 技能。这与"敌方有大招才需要预留净化"在语义上完全对齐：4 级前敌方根本没法放大招，反向 mask 此时本来就不会触发（条件 `_enemy_ult_cast_frame` 仍为 None），等级判定 `>=4` 与 `>4` 的可观察差异主要落在"4 级解锁的那一波兵线"——`>=4` 更早进入约束态、更安全。

### 2.8 监控指标（落地时一并加）

参考 `cleanse_override_count` 的样板 (`workflow/train_workflow.py:243-244` + `monitor_builder.py:81`)：
- `skill2_blocked_count`：每局被反向 mask 拒掉的次数；
- `skill2_cast_outside_window_count`：未 mask 但仍释放在窗口外的次数（保留作 sanity check，理论上应为 0）；
- `skill2_cleanse_rate`：mirror 对局中 `cleanse_override_count / max(1, skill2_total_cast_count)`，理想 → 1；
- `enemy_cleansed_us_count`：敌方在我们大招命中其后用 2 净化的次数。已从 reward 公式剥离（§2.6），现在仅作日志监控。

### 2.9 不做 / 暂缓的事

| 项 | 决定 | 理由 |
|---|---|---|
| 非镜像 (133v112) 加 mask | 不做 | 鲁班大招无 CC，2 技能在该对局有 AS/MS buff 用途，不能封死 |
| 把 misuse 从 `cleanse_success` 剥离成独立 reward 项 | 暂缓 | 硬 mask 落地后软惩罚不再触发（模型无法采样到 misuse 动作），剥离价值降低；先看 mask 效果再决定 |
| 改 `_is_in_berserk_engagement` 判据 | 暂缓 | 仅服务于狂暴 `berserk_timing`，与本次 2 技能改动解耦；如果狂暴乱放也出现再说 |

## 3. 狂暴召唤师技能 (80110)：60 帧无输出加重惩罚

### 3.1 规则原文（用户给定）

> 狂暴再加一个：如果开启后 60 帧内未对敌方小兵 / 英雄 / 防御塔造成伤害，则给一个较高的惩罚。

### 3.2 与现有 `berserk_timing` 的关系

当前 `berserk_timing` (`reward_process.py:928-948`) 用 **位置判据** 评估狂暴时机：
- `BERSERK_LOOKAHEAD_FRAMES = 20` 帧 look-ahead；
- 进入 `_is_in_berserk_engagement`（敌方存活且距离 ≤ 7000）→ `BERSERK_GOOD_REWARD = +0.5`；
- 20 帧仍未进入 → `BERSERK_WASTED_REWARD = -0.8`。

它能抓"放完狂暴跟敌人不在一起"的位置错误，**但不能抓"贴着敌人放完没打出输出"** 这种另一类浪费——例如释放后被对方风筝、自己空 A 落地、走位失误等。本节新增的判据基于 **实际造成的伤害事件**，与位置判据正交。两者并存，对同一次错误施放可同时扣分（−0.8 + −1.5 = −2.3 上限），既能压住位置错误也能压住"贴脸但没输出"的浪费。

### 3.3 新增 reward 项：`berserk_no_damage_penalty`

**触发逻辑（每帧执行）**：

1. 维护两个实例状态：
   - `self._berserk_damage_check_frame: Optional[int]`：本次狂暴的检查起始帧；未在监控期则为 `None`。
   - `self._berserk_damage_dealt_in_window: bool`：监控期内是否已观察到本方造成伤害。

2. 每帧判断本方是否释放了 80110：复用 `_used_skill_by_config(main_hero, GameConfig.BERSERK_SKILL_ID)`，该函数内部用 `succUsedInFrame > 0` 检测单帧边沿（见 §2.3 的 `succUsedInFrame` 定义）。一旦边沿出现：

   ```text
   self._berserk_damage_check_frame = frame_no
   self._berserk_damage_dealt_in_window = False
   ```

   即使 60 帧窗口未结束就再次释放（理论上不可能，CD 远大于 60 帧），覆盖式重启监控。

3. 监控期内（`self._berserk_damage_check_frame is not None`）：

   ```text
   if self._has_dealt_damage_to_enemy_units(frame_data, main_hero):
       self._berserk_damage_dealt_in_window = True
   ```

   `_has_dealt_damage_to_enemy_units` 的判定见 §3.4。一旦置 True 即不再翻回 False。

4. 当 `frame_no - self._berserk_damage_check_frame >= 60` 时结算：

   ```text
   if self._berserk_damage_dealt_in_window:
       value = 0.0          # 有输出，不扣
   else:
       value = -1.5         # 较高惩罚
   self._berserk_damage_check_frame = None
   self._berserk_damage_dealt_in_window = False
   return value
   ```

   否则窗口未到，本帧贡献 `0.0`。

5. **新局重置**：在 `__init__` / `reset` 中将上述两字段置 `None` / `False`。

### 3.4 "造成伤害" 的判定（写死）

数据来源：`take_hurt_infos` 是受害者上的列表，每条含 `atker / attacker`（攻击者 runtime_id）与 `skillSlot / skill_slot`、`hurt`（数值）等字段。已经在仓库内大量复用（见 `reward_process.py:576, 583, 647, 860`）。

具体扫描范围（敌方阵营，对应用户规则"敌方小兵 / 英雄 / 防御塔"）：

```text
main_runtime = self._actor_runtime(main_hero)
main_camp    = self.main_hero_camp

# 敌方英雄
for hero in frame_data.get("hero_states", []) or []:
    if _camp_key(_get(hero, "camp")) == _camp_key(main_camp):
        continue
    for hurt in _get(hero, "take_hurt_infos", []) or []:
        if _get_any(hurt, ["atker", "attacker"], None) == main_runtime:
            return True

# 敌方小兵 + 敌方防御塔（都来自 npc_states）
for npc in frame_data.get("npc_states", []) or []:
    sub_type = _get_any(npc, ["sub_type", "subType"], None)
    if sub_type not in SOLDIER_SUB_TYPES and sub_type not in TOWER_SUB_TYPES:
        continue   # 排除野怪、蛋糕等其他 NPC
    if _camp_key(_get(npc, "camp")) == _camp_key(main_camp):
        continue   # 排除己方单位
    for hurt in _get(npc, "take_hurt_infos", []) or []:
        if _get_any(hurt, ["atker", "attacker"], None) == main_runtime:
            return True

return False
```

要点：
- 沿用项目已有的 `SOLDIER_SUB_TYPES = {1, "1", 11, "11", "ACTOR_SUB_SOLDIER"}` 与 `TOWER_SUB_TYPES = {21, "21", "ACTOR_SUB_TOWER"}`（`reward_process.py:15-16`），与用户规则的"小兵 / 防御塔"语义对齐。
- 不计野怪（neutral 阵营、`sub_type` 不在 SOLDIER/TOWER 集合内）、不计蛋糕（不属于 npc 攻击对象）；与用户列出的三类对象一致。
- 攻击者过滤用 `runtime_id` 严格匹配 `main_hero`，不会把本方小兵打出的伤害算到我方头上。
- 普攻、技能伤害、技能 DOT、被动伤害都通过 `take_hurt_infos` 统一表现，无需分别识别 `skillSlot`，所以一次扫描可一并覆盖。

### 3.5 reward 项接入

1. `conf.py REWARD_WEIGHT_DICT` 新增：

    ```python
    "berserk_no_damage_penalty": 1.0,
    ```

    与 `berserk_timing` 权重一致（事件值本身就是 0 / −1.5，权重 1.0 后即−1.5）。

2. `conf.py REWARD_TIME_SCALE_OVERRIDES` 新增 `"berserk_no_damage_penalty": 0.0`——与 `berserk_timing` 一致，不做时间衰减（晚期狂暴乱放与早期同样致命）。

3. `reward_process.py` 在 `frame_data_process` 里调用 `_detect_berserk_no_damage_penalty(frame_data, main_hero, frame_no)` 写入 `self._berserk_no_damage_penalty_value`；`set_cur_calc_frame_vec` 在 `if reward_name == "berserk_no_damage_penalty"` 分支下，沿用 `berserk_timing` 那条的"仅 main 侧赋值，enemy 侧置 0" 模式（即非零和、主侧专属）。

4. `get_reward` 里直接复用主侧 `cur_frame_value`，与 `berserk_timing` 同处理路径。

### 3.6 关于"较高" 的数值

- 现有 `BERSERK_WASTED_REWARD = -0.8`（位置错），本节新增 `BERSERK_NO_DAMAGE_PENALTY = -1.5`（输出错），约为 1.9×。
- 与单次 `death` 基础值 −1.0 同量级（`death` 还有时段乘子 0.7 / 1.3）；与一次 `kill` 正奖 +0.8 形成不对称——即"乱放狂暴一次" 比 "击杀对方" 的代价还高，强迫模型只在能打出伤害的场景使用。
- 若实际训练曲线显示 `berserk_total_cast_count` 大幅下降到狂暴几乎不放（过度抑制），把权重从 1.0 降到 0.5（净惩罚 −0.75）再观察。

### 3.7 监控指标（落地时一并加）

- `berserk_total_cast_count`：每局狂暴释放总次数；
- `berserk_no_damage_count`：每局狂暴释放后 60 帧无输出的次数；
- `berserk_no_damage_rate = berserk_no_damage_count / max(1, berserk_total_cast_count)`：理想 → 0。

监控指标接入位置与 §2.8 相同：`workflow/train_workflow.py` 累计字段 + `monitor_builder.py` 注册。

### 3.8 边界与不做的事

| 项 | 决定 | 理由 |
|---|---|---|
| 把 `berserk_no_damage_penalty` 合并进 `berserk_timing` | 不做 | 两者语义正交（位置 vs 输出），独立项便于单独监控/单独调参/单独回滚 |
| 把"野怪"也算进伤害目标 | 不做 | 用户规则文字明确只列"敌方小兵/英雄/防御塔"，且野怪伤害不是 1v1 主线 |
| 60 帧改为基于技能持续时间动态判定 | 不做 | 80110 的实际加伤持续时间也在 60 帧量级，60 帧已经覆盖整个 buff 窗口；动态判定增加复杂度无收益 |

## 4. 狄仁杰大招命中后续追打 (`direnjie_skill3_followup_damage`) 改为多次累计

### 4.1 改动

`reward_process.py` 中的 `_detect_direnjie_skill3_followup_damage` 与配套状态字段改造，**权重不动**（`conf.py:76` 维持 0.10）：

| 项 | v2.0 | v2.1 |
|---|---|---|
| 窗口长度 | `DI_RENJIE_SKILL3_FOLLOWUP_WINDOW = 30` 帧 | 不变 |
| 触发起点 | 大招命中敌方英雄那一帧 | 不变 |
| 单帧检测 | 是否存在 `enemy_hero.take_hurt_infos` 中 `attacker == main_runtime` 的条目 | 不变 |
| **每次大招命中的累计上限** | **1 次** (`pending_direnjie_skill3_followup_used: bool` 一旦置 True 立即结束) | **8 次** (`pending_direnjie_skill3_followup_count: int` 累计到 8 后停止) |
| 单次事件值 | 1.0 | 1.0 |
| 权重 | 0.10 | 0.10 |
| 单次大招命中后追打的 reward 上限 | `1 × 1.0 × 0.10 = 0.10` | `8 × 1.0 × 0.10 = 0.80` |

### 4.2 改造后的检测逻辑（写死）

替换 `_detect_direnjie_skill3_followup_damage`（`reward_process.py:841-855`）和相关状态字段。

**状态字段**（`__init__` / `reset` 初始化）：

```python
self.pending_direnjie_skill3_followup_frame = None   # 不变
self.pending_direnjie_skill3_followup_count = 0      # 新增；替代 _used: bool
```

**算法（每帧执行）**：

```text
const CAP = 8

if pending_direnjie_skill3_followup_frame is None:
    return 0.0

elapsed = frame_no - pending_direnjie_skill3_followup_frame
if elapsed > DI_RENJIE_SKILL3_FOLLOWUP_WINDOW:   # 30 帧窗口过期
    pending_direnjie_skill3_followup_frame = None
    pending_direnjie_skill3_followup_count = 0
    return 0.0

if pending_direnjie_skill3_followup_count >= CAP:
    return 0.0   # 累计已达上限，窗口剩余帧不再累加

if _enemy_hero_damaged_by_main(enemy_hero, main_runtime):
    pending_direnjie_skill3_followup_count += 1
    return 1.0

return 0.0
```

**触发起点（`_compute_skill_hit_events` 内已有，不动）**：

```python
if hero_counts.get("direnjie_skill3_hit_enemy_hero", 0.0) > 0:
    self.pending_direnjie_skill3_followup_frame = frame_no
    self.pending_direnjie_skill3_followup_count = 0   # 重置计数，覆盖式重启
```

**事件粒度（说明性）**：

- 每帧最多 +1，**不**按 `take_hurt_infos` 内条目数累加；AOE / 命中多目标在同一帧只算一次。理由：避免普攻命中多个单位时同一动作被多计；项目内其他 `_count_skill_hits_on` 也采用"帧粒度计数"。
- 平 A / 技能 / 被动伤害都通过 `take_hurt_infos` 表现，统一计入，不区分。

### 4.3 数值校准与收益曲线

| 追打质量 | 事件计数 | 总 reward (× 0.10) | 与其他通道对比 |
|---|---|---|---|
| 大招命中后立即脱离 / 0 次追打 | 0 | 0 | 损失全部追打收益 |
| 1 次追打（v2.0 上限） | 1 | 0.10 | 与 v2.0 等价 |
| 3-4 次追打（典型平 A 风筝节奏） | 3-4 | 0.30-0.40 | 接近 `direnjie_skill3_hit_enemy_hero` 0.40 |
| 满 8 次追打（拖住整个减速窗口） | 8 | 0.80 | 与 `kill` 0.80 等价 |

设计意图：
- **保留 v2.0 上限**：1 次追打仍能拿 0.10，没有让"只追一下"的样本变弱。
- **奖励持续输出**：3-4 次的"典型平 A 风筝"行为，从 v2.0 的 0.10 提升到 0.30-0.40，与大招命中本身的 0.40 同量级，向模型明确"减速窗口要被吃满"。
- **总封顶 0.80 = kill**：相当于告诉模型"追满 30 帧减速 ≈ 一次击杀"的隐含价值，但永远不超过一次真实击杀，避免与击杀路径冲突。
- 取 **CAP = 8** 的原因：30 帧 ÷ 平 A 间隔（狄仁杰平 A 大约 4-5 帧 / 次，前期 1.0 攻速）≈ 6-7 次。CAP 8 略宽于满输出节奏，留余量给"被动叠层后攻速提高"的情形；取 5 会过早封顶（攻速一加就吃不完），取 10 等同于不封顶（30 帧不可能平 A 满 10 次）。

### 4.4 监控

`reward_direnjie_skill3_followup_damage` 在 `monitor_builder.py:119` 已存在，但 v2.1 后单局均值会从 ~0.1 量级跳到 ~0.3-0.5（同一频次 × 更高累计），需要把面板的 y 轴上限调高，否则曲线会顶在面板上沿。

新增（可选，便于诊断）：
- `direnjie_skill3_followup_count_per_ult`：每次大招命中后实际累计的事件次数（直方图）。若分布集中在 0-1，说明模型仍未学会追打；集中在 7-8，说明 CAP 设得偏紧，可放宽到 10。

### 4.5 边界与不做的事

| 项 | 决定 | 理由 |
|---|---|---|
| 把权重也从 0.10 提到 0.30 | **不做**（撤回） | 现在通过多次累计已经把"持续输出"的总收益拉起来；再叠加权重会让上限到 2.4，远超 kill 0.80，过强 |
| 同时把窗口放到 60 帧 | 不做 | 30 帧已经覆盖大招减速期；放宽窗口会让"追打"与"自然普攻清线" 混淆 |
| 按 `hurt` 数值（伤害量）发奖励 | 不做 | 与项目内其他 skill_hit reward 风格不一致；伤害量受装备/等级污染，事件计数更稳 |
| 同时放宽 CAP 到 10 | 暂缓 | 8 是合理首选；上线后看 `direnjie_skill3_followup_count_per_ult` 分布再决定 |

## 5. 预期效果与回滚

### 5.1 预期

- 镜像对局 2 技能日均施放次数 ↓，`cleanse_override_count` 占比 ↑（接近 100%）。
- `cleanse_success` reward 在 mirror 对局的方差 ↓，正样本密度 ↑。
- 狂暴 `berserk_no_damage_rate` 从初期较高水平逐步收敛至接近 0；`berserk_total_cast_count` 不应明显下滑（仍是有用召唤师技能）。
- 狄仁杰大招命中 → 30 帧内追打事件累计次数提升；`reward_direnjie_skill3_followup_damage` 均值从 ~0.1 量级跳到 ~0.3-0.5（典型 3-4 次追打 × 0.10）。
- 不应该看到的事：mirror 之外的胜率回退（2 技能 mask 不在那些对局触发；狂暴惩罚则全对局都生效，但抑制的是"放空"行为，不应负面影响整体胜率）；狄仁杰追打改造应是单调改善，若胜率下降则 CAP 从 8 调回 5 或恢复 v2.0 单次 cap。

### 5.2 回滚

- 2 技能 mask：`_maybe_block_skill2` 是单一函数，删除函数 + 删除 predict/exploit 两处调用即可恢复 v2.0 行为。
- `cleanse_success` 公式：把 `- self._cleanse_enemy_count` 加回 `reward_process.py:208` 即可。
- 狂暴 60 帧无输出惩罚：从 `REWARD_WEIGHT_DICT` 删 key + 删除 `_detect_berserk_no_damage_penalty` 及其状态/调用即可；reward 项数变化需重启 reverb buffer（与正常 reward 增删一致）。
- 狄仁杰追打检测改造：`pending_direnjie_skill3_followup_used: bool` 字段改回原版，`_detect_direnjie_skill3_followup_damage` 内 `_used = True` 早返回那一段恢复（删除 `_count` 字段和 CAP 判定），即可回 v2.0 行为；权重未动，无需重建 buffer。

整体无网络 / 特征改动，**网络权重可以热启动**；仅狂暴新增项需要重建 reverb buffer。

### 5.3 风险

1. **预判净化场景被误封**：敌方刚抬手放大招、技能弹道飞行途中——根据 §2.3 的定义，敌方 slot 3 在抬手帧就会出现 `succUsedInFrame > 0`，`_enemy_ult_cast_frame` 在那一帧被立刻更新，此后 300 帧 mask 解除，我方反而**允许**先手 2 技能拉开身位避招。所以这一项实际上是改善而非风险。
2. **过早收敛**：硬 mask 杜绝了"主动用 2 技能开 buff 入场"的探索路径。若发现策略在 mirror 对局显得过于被动（只敢被打了才放 2），考虑把规则放宽为"敌方近 300 帧未释放 ult **且** 我方 hp_rate > 0.6 才 mask"——hp 低时允许提前放 2 自给 AS/MS。
3. **删除零和净化项后敌方净化频次上升的副反馈**：mask 落地后我方 2 技能更稀疏 → 敌方更容易找到机会净化我方大招，`enemy_cleansed_us_count` 预期上升。这本身不是问题，但若发现我方开大招频次也跟着下降（说明 critic 通过 hp/kill 等其他通道间接学到"开大招容易被净化"的负反馈），则说明剥离零和项的判断成立，无需回滚；若我方开大率反而上升、命中率下降，则考虑用更小权重把该项加回来（如 0.05 而非原来等权 0.15）。
4. **狂暴过度抑制**：60 帧 −1.5 的惩罚在训练初期可能让模型直接学到"永远不放狂暴" 这一退化策略（避免任何 −1.5 风险，但也错过所有 +0.5 收益）。监控 `berserk_total_cast_count`：如果 50 ckpt 后稳定低于 v2.0 同期 50%，先把权重降到 0.5；若仍过低，再把窗口从 60 改到 90（更宽松的判定）。
5. **`take_hurt_infos` 帧粒度假设**：本设计假设该字段是"当前帧的受击事件"，与项目内 `_compute_cleanse_events`、`_count_skill_hits_on` 的用法一致。落地时第一局 dump 验证一下两点：(a) 同一次普攻不会在多帧重复出现；(b) hp 下降事件能可靠对应 take_hurt_infos 条目。两者都成立才继续推全量训练。
6. **狄仁杰追打过度抑制清线**：累计上限 8 × 权重 0.10 = 0.80 与 `kill` 等价，可能让模型在大招命中后"死磕单一敌方英雄而忽略清线 / 防御塔"。监控 `last_hit` 与 `tower_hp_point` 增长率，若清线节奏显著退化，把 CAP 从 8 调回 5。
