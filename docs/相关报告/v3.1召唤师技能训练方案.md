# v3.1 召唤师技能训练方案

## 1. 背景

当前 `agent_diy` 的召唤师技能逻辑存在训练/评估分布不一致：

- 训练局 `is_eval=False` 时，双方都会走 `SUMMONER_SKILL_TRAIN_MODE = "cycle"`，在候选列表中轮换召唤师技能。
- 当前 112/133 的训练候选均为 `[80110, 80115, 80102]`，即狂暴、闪现、治疗。
- 评估/比赛局 `is_eval=True` 时，双方固定走 `DEFAULT_SUMMONER_SKILL = 80110`，即狂暴。

这会让同一个 button 8 在训练中承担三种不同语义：狂暴开战、闪现位移、治疗保命。虽然特征里包含召唤师技能信息，但 PPO 需要同时学习三套使用策略，最终比赛只使用狂暴，样本效率和策略一致性都不理想。

近期现象是模型不爱放狂暴，或者已经与敌方英雄对打到一半才放。除狂暴空放惩罚偏重外，训练中混入闪现/治疗也会稀释“button 8 = 狂暴开战窗口”的行为学习。

新的讨论结论是：后续主训练候选从“狂暴/闪现/治疗”改为“狂暴/弱化”。狂暴 `80110` 与弱化 `80121` 都按“英雄换血增益型召唤师技能”处理，统一语义为：在对英雄换血窗口开启 button 8，以提高对拼收益。暂不在特征语义和奖励语义上强行区分二者。

## 2. 当前 selfplay 采样事实

当前 selfplay 是双边采样。

在 `agent_diy/workflow/train_workflow.py` 中，`reset_agents()` 初始设置：

```python
self.do_predicts = [True, True]
self.do_samples = [True, True]
```

当 `opponent_agent == "selfplay"` 时，非 monitor_side 的一侧只执行：

```python
agent.load_model(id="latest")
```

没有把 `do_samples[i]` 置为 `False`。因此 selfplay 局中：

- 蓝红双方都加载 latest；
- 蓝红双方都由当前模型预测动作；
- 蓝红双方都采样；
- 采样数据都会进入 learner。

这意味着 selfplay 不是“固定一方为学习方，另一方为对手方”，而是同一策略在双方阵营同时训练。

## 3. 推荐目标

后续训练目标应与最终评估/比赛对齐：

- 我方最终模型只在狂暴 `80110` 与弱化 `80121` 两个候选中选择。
- 训练期让模型充分见到狂暴和弱化两种 button 8 效果。
- 比赛时可以根据分 matchup 评估结果选择狂暴、弱化，或按英雄对阵表选择。
- 训练中不再混入治疗/闪现，避免 button 8 同时承担保命恢复或位移语义。

## 4. 训练方案

### 4.1 selfplay：双方同技能，狂暴/弱化按局轮换

selfplay 局建议保持双方召唤师技能相同，并在 episode 级别于狂暴 `80110` 与弱化 `80121` 间轮换或 50/50 随机。

推荐形式：

- 第 N 局：双方都狂暴 `80110`；
- 第 N+1 局：双方都弱化 `80121`；
- 或者每局随机选择一个技能，但蓝红双方使用同一个技能。

原因：

1. 当前 selfplay 是双边采样，如果一边狂暴、一边弱化，同一个 learner 会同时收到两种不对称角色样本，技能强弱差异也会混入策略梯度。
2. 双方同技能可以保持自对弈分布对称，让模型主要学习“何时在英雄换血窗口按 button 8”。
3. episode 级轮换能让模型同时见到狂暴与弱化，又避免同一局内的非对称技能噪声。

结论：只要 selfplay 继续双边采样，就不应在 selfplay 中让双方召唤师技能不对称。

### 4.2 历史模型训练：双方狂暴/弱化独立随机

历史模型局建议：

- monitor_side / 学习方：在狂暴 `80110` 与弱化 `80121` 间随机或轮换。
- 历史模型对手侧：在狂暴 `80110` 与弱化 `80121` 间随机或轮换。
- 学习方和历史模型对手侧可以独立随机，不要求相同。
- 历史模型侧不采样，继续作为环境对手分布。

需要覆盖四种技能组合：

- 我方狂暴 vs 对方狂暴；
- 我方狂暴 vs 对方弱化；
- 我方弱化 vs 对方狂暴；
- 我方弱化 vs 对方弱化。

原因：

1. 历史模型侧不进入 learner，因此它的技能随机主要作为对手分布扰动。
2. 学习方也要同时训练狂暴/弱化，否则比赛时不能可靠切换到未充分训练过的技能。
3. 独立随机能让模型学会在不同敌方技能条件下使用自己的换血技能。
4. 该设计能为最终“比赛选狂暴还是弱化”提供更完整的胜率依据。

该设计适用于当前 `opponent_agent` 为自定义模型 ID 的训练局，因为代码路径里历史模型侧 `do_samples[i] = False`。

### 4.3 评估：分技能组合统计

评估不应只看一个混合胜率，而应拆开统计技能组合：

- 我方狂暴 vs 对方狂暴；
- 我方狂暴 vs 对方弱化；
- 我方弱化 vs 对方狂暴；
- 我方弱化 vs 对方弱化。

如果实际比赛对手技能未知，则重点看：

- 我方狂暴的平均胜率；
- 我方弱化的平均胜率；
- 四个英雄 matchup 下的分项胜率。

最终 `init_config()` 按 `SUMMONER_SKILL_MATCHUP_WINRATE` 中的 `(my_hero, opponent_hero) -> skill winrate` 表自动选择胜率更高的技能；表为空或打平时回退到默认狂暴 `80110`。

## 5. 不推荐方案

### 5.1 selfplay 中一方狂暴、一方弱化且双边采样

不推荐。

原因是当前 selfplay 双边样本都会训练同一个 learner。若蓝方固定狂暴、红方固定弱化，模型会同时学习：

- 作为狂暴方如何按 button 8；
- 作为弱化方如何按 button 8；

这会把不对称技能胜负关系也写进同一个策略更新。若要比较狂暴和弱化强弱，应该通过评估组合统计，而不是在双边采样 selfplay 中直接制造不对称。

除非改成单边采样 selfplay，即只采样一侧，把另一方当不学习的对手，否则不应在 selfplay 中做召唤师技能不对称。

### 5.2 继续训练期混入治疗术或闪现

不推荐作为当前阶段主训练分布。

治疗术 `80102` 的 button 8 语义是低血量保命，闪现 `80115` 的 button 8 语义是位移，与狂暴/弱化的“换血增益”语义不同。当前阶段应先把 button 8 训练成对英雄换血窗口技能，再讨论是否引入其他技能。

## 6. 建议实现口径

后续实现时建议增加“按对手类型选择召唤师技能”的配置，而不是继续只依赖 `is_eval`：

| 对局类型 | 学习方技能 | 对手方技能 | 是否双边采样 |
| --- | --- | --- | --- |
| selfplay | 80110 或 80121 | 与学习方相同 | 是 |
| 历史模型训练 | 80110 / 80121 独立随机 | 80110 / 80121 独立随机 | 否，仅学习方采样 |
| common_ai 训练 | 80110 / 80121 | 80110 / 80121 或按环境可控能力固定 | 否 |
| eval / exam | 按评估组合指定 | 按评估组合指定 | 否或只统计，不训练 |

实现边界：

- 不改 action space。
- 不改 `LABEL_SIZE_LIST`。
- 当前主训练候选只保留狂暴 `80110` 与弱化 `80121`。
- 比赛阶段允许根据评估胜率选择狂暴或弱化。
- 不让治疗术、闪现进入当前主训练候选。
- 历史模型侧的狂暴/弱化选择用于扰动对手分布；历史模型侧不作为当前 learner 的训练目标。

## 7. 奖励设计待讨论

奖励设计后续继续细化。当前已确定的原则和第一版严格判定如下：

- 狂暴和弱化先共用一套“换血召唤师技能”时机奖励。
- 核心语义是：敌方英雄可见、即将进入或已经进入真实对打窗口时释放，释放后应发生足够强度的英雄交互。
- 暂不把狂暴标成偏进攻、弱化标成偏防守；先统一视为对英雄换血增益。
- 惩罚要温和，避免模型学到“不按 button 8 最安全”。
- 继续监控 `summoner_skill_used_count`、按技能拆分的释放次数、释放后无英雄交互比例、分 matchup/技能胜率。

### 7.1 真实对打判定

一次狂暴/弱化释放后，开启 `90` 帧检查窗口。只有满足“真实对打”才给主奖励；只蹭到少量伤害给 `0`，不奖不罚。

初版严格条件：

- 检查窗口：`DUEL_SUMMONER_WINDOW = 90`。
- 距离阈值：`DUEL_SUMMONER_RANGE = 8500`。
- 伤害阈值：窗口内英雄伤害达到 `max_hp * 0.20` 量级。可按我方对敌方、敌方对我方、或双方总英雄伤害三种统计口径实现，但阈值必须对应 20% 血量级别，避免把试探消耗计为好释放。
- 持续交互阈值：窗口内至少 `5` 次英雄伤害交互。
- 不使用 `close_frame_count >= 25` 这类持续接近硬条件；距离只用于判断释放是否处在合理对打范围或明显远离。

建议奖励分层：

- 真实对打：`+0.8`。
- 有少量英雄伤害但未达到 20% 血量阈值或不足 5 次英雄伤害交互：`0`。
- 明显空放：`-0.4`。

核心目标不是让模型无脑释放召唤师技能，而是让模型在可预期真实对打窗口前后按 button 8，并在释放后进入足够强度的英雄换血。

## 8. 推荐结论

推荐采用：

1. 当前主训练候选改为狂暴 `80110` 与弱化 `80121`。
2. selfplay 双方同技能，按局在狂暴/弱化间轮换或 50/50 随机。
3. 历史模型训练中，学习方与对手方都在狂暴/弱化间独立随机；历史模型侧不采样。
4. 评估拆分统计四种技能组合，并按英雄 matchup 记录胜率。
5. 比赛时可以根据评估结果固定选择强技能，或按 `112/133` 对阵表选择技能。
6. 暂时移除治疗术、闪现主训练候选。
7. 后续奖励用一套“换血召唤师技能”奖励统一覆盖狂暴和弱化。

该方案把 button 8 的训练语义收敛为“英雄换血增益”，同时允许通过评估数据决定比赛携带狂暴还是弱化。关键约束是：比赛要选择的技能必须在训练中充分出现，不能训练只带一种技能、比赛临时切到另一种。

## 9. Matchup 胜率监控与比赛选择

训练内评估按 `(我方英雄, 对方英雄, 召唤师技能)` 上报 count/win：

- `eval_m112_o112_s80110_count` / `eval_m112_o112_s80110_win`
- `eval_m112_o112_s80121_count` / `eval_m112_o112_s80121_win`
- `eval_m112_o133_s80110_count` / `eval_m112_o133_s80110_win`
- `eval_m112_o133_s80121_count` / `eval_m112_o133_s80121_win`
- `eval_m133_o112_s80110_count` / `eval_m133_o112_s80110_win`
- `eval_m133_o112_s80121_count` / `eval_m133_o112_s80121_win`
- `eval_m133_o133_s80110_count` / `eval_m133_o133_s80110_win`
- `eval_m133_o133_s80121_count` / `eval_m133_o133_s80121_win`

每个组合的胜率为：

```text
eval_m{my}_o{opp}_s{skill}_win / eval_m{my}_o{opp}_s{skill}_count
```

比赛/正式评估时，`Agent.init_config()` 不会走训练 workflow 的 forced skill，而是读取 `GameConfig.SUMMONER_SKILL_MATCHUP_WINRATE`。后续把上述监控统计出的稳定胜率写入该表，即可按 `112/133` 对局自动选择狂暴或弱化。
