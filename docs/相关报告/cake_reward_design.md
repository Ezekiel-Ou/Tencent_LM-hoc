# 血包奖励与被打断惩罚设计

## 背景

当前奖励中，英雄血量主奖励 `hp_point` 已经使用血量函数做逐帧 shaping：

```python
f(hp_rate) = hp_rate ** 0.25
```

也就是奖励的核心血量信号，已经不再是线性血量，而是函数变换后的血量值。

但血包奖励 `cake_pickup` 仍然采用固定分档：

- `hp < 0.2` 时奖励 `+1.0`
- `0.2 <= hp < 0.5` 时奖励 `+0.5`
- `0.5 <= hp <= 0.8` 时奖励 `+0.3`
- `hp > 0.8` 时惩罚 `-0.5`

这种设计和 `hp_point` 的口径已经不一致，容易带来两个问题：

1. 血包收益和血量函数脱钩，奖励尺度不统一。
2. 吃血包事件奖励和血量逐帧奖励叠加后，可能出现局部过强或过弱。

因此，血包奖励和血包被打断惩罚都应该围绕同一个血量函数重新设计。

## 设计目标

新的血包奖励设计应满足以下目标：

1. 与 `hp_point` 使用同一套血量价值函数。
2. 鼓励低血时成功吃血包。
3. 抑制高血量浪费血包。
4. 对“明确尝试吃血包但失败”的行为给出轻量惩罚。
5. 不让血包事件奖励压过主血量 shaping、击杀、死亡、推塔等奖励。

## 核心原则

血包奖励不应再主要承担“奖励回血”本身的职责，因为回血已经由 `hp_point` 逐帧反映。

新的血包奖励应该拆成两部分：

1. `血量收益`
2. `资源获取事件奖励`

其中：

- `血量收益` 体现“这次吃包对当前血量状态到底有多大帮助”
- `资源获取事件奖励` 体现“成功拿到地图资源本身是好事”

## 血量函数口径

定义血量价值函数：

```python
f(hp_rate) = hp_rate ** 0.25
```

其中：

- `hp_rate = hp / max_hp`
- `hp_rate` 取值范围为 `[0, 1]`

这个函数有两个特点：

1. 低血区更敏感
2. 高血区更平滑

因此，用它来衡量吃血包收益，会自然地让“残血吃包”比“高血吃包”更有价值。

## 血包成功奖励设计

### 1. 基础形式

建议将血包成功奖励定义为：

```python
cake_success_reward = resource_bonus + alpha * max(0, f(hp_after) - f(hp_before))
```

其中：

- `hp_before`：吃到血包前的血量比例
- `hp_after`：吃到血包后的血量比例
- `resource_bonus`：成功获取血包的固定小奖励
- `alpha`：血量函数增量的缩放系数

### 2. 含义解释

`resource_bonus` 负责告诉策略：

- 成功抢到血包本身是有价值的

`alpha * max(0, f(hp_after) - f(hp_before))` 负责告诉策略：

- 同样是吃到血包，低血时吃到更赚
- 高血时吃到收益更小

### 3. 为什么不直接只用固定分档

固定分档虽然简单，但有明显缺点：

1. 与 `hp_point` 口径不一致
2. 难以适应后续血量函数修改
3. 奖励边界不平滑，容易产生阈值抖动

而函数增量形式具备更好的统一性和可维护性。

### 4. 为什么不只用增量，不加固定 bonus

如果只保留：

```python
alpha * (f(hp_after) - f(hp_before))
```

那么血包事件会和 `hp_point` 高度重合，容易退化成“只是再重复奖励一次回血”。

加上一个较小的 `resource_bonus` 后，可以保留“资源争夺成功”的独立语义。

## 高血量浪费血包惩罚

高血时乱吃血包应保留惩罚，但不建议再采用过重的固定负值。

建议触发条件：

```python
hp_before > high_hp_threshold
and recovered_hp < small_gain_threshold
```

满足时给出：

```python
cake_waste_penalty = -beta
```

其中：

- `high_hp_threshold`：高血阈值，例如 `0.8` 或 `0.85`
- `small_gain_threshold`：实际回血很少的阈值
- `beta`：轻到中等强度惩罚

### 设计意图

这个惩罚不是为了严格禁止高血吃包，而是为了抑制明显浪费资源的行为。

因此需要满足两个条件：

1. 吃包前血量确实已经很高
2. 这次吃包的实际恢复量也很小

这样可以避免误伤一些边界情况。

## 血包被打断惩罚设计

### 1. 为什么需要单独设计

如果英雄为了吃血包而走位，但最后没有吃到，当前系统里通常只会通过以下方式体现损失：

1. 吃不到血包，因此拿不到成功奖励
2. 如果过程中被打掉血，会收到 `hp_point` 的负反馈

这还不够，因为“争夺血包失败”本身是一个离散决策失败事件。

因此，建议补充一个轻量的“血包被打断惩罚”，但它不能过重，否则会让智能体过度害怕争夺血包。

### 2. 什么叫“被打断”

不建议把所有“没吃到血包”的情况都算作被打断，因为噪声会很大。

建议只对“明确发生了吃血包尝试，但最终失败”的情况处罚。

### 3. 建议的状态机

血包逻辑建议使用一个 `pending_cake_attempt` 状态：

```python
attempt -> pending -> success / interrupted / abandoned
```

三种状态含义如下：

- `attempt`：满足吃血包尝试条件，开始跟踪一次争夺事件
- `success`：在确认窗口内成功吃到血包
- `interrupted`：在确认窗口内明确失败
- `abandoned`：不够确定，不给奖惩，直接取消跟踪

### 4. attempt 触发条件

建议同时满足以下条件时创建一次 `pending_cake_attempt`：

1. 我方血量低于阈值，例如 `hp_rate < 0.5`
2. 附近存在可争夺血包
3. 我方进入血包争夺范围，或正在明显靠近血包
4. 当前未在跟踪其他血包尝试

可记录的信息包括：

- `attempt_frame`
- `target_cake_pos`
- `hp_at_attempt`
- `hp_func_at_attempt`
- `distance_at_attempt`
- `enemy_distance_at_attempt`

### 5. success 判定

在确认窗口内，如果满足以下条件，可判定为成功：

1. 血包消失
2. 我方距离该血包最近，或不晚于敌方到达
3. 我方血量或血量函数值出现正向增长

成功后发放 `cake_success_reward`，并清空 pending 状态。

### 6. interrupted 判定

建议将以下情况视为“被打断”：

1. 已经建立了 `pending_cake_attempt`
2. 在短窗口内未成功吃到血包
3. 同时满足以下任一条件：

- 血包消失，但敌方更可能吃到
- 我方在尝试期间受到明显伤害
- 我方被迫远离血包区域
- 我方死亡

此时给出：

```python
cake_interrupt_penalty = -gamma
```

### 7. abandoned 判定

如果只是轻微靠近过血包，但没有形成明确争夺，例如：

- 我方本来就只是路过
- 血包距离较远
- 没有持续靠近趋势

则应取消 pending，不给奖惩。

这样可以减少误判和奖励噪声。

## 被打断惩罚的强度原则

被打断惩罚一定要比成功奖励弱。

建议满足以下关系：

```text
|cake_interrupt_penalty| < cake_success_reward
```

并且：

```text
|cake_interrupt_penalty| < 一次中等掉血带来的 hp_point 负反馈
```

原因是：

1. 争夺血包失败的主要代价，本来就应由掉血 shaping 体现
2. 被打断惩罚只负责补一个“资源争夺失败”的离散信号
3. 如果这个惩罚太大，策略会学成“不敢争血包”

## 和 `hp_point` 的关系

这是设计中最重要的一点。

`hp_point` 已经会自动对血量变化进行奖励或惩罚，因此：

1. 血包成功奖励不能过大，否则会对回血事件双重放大
2. 血包被打断惩罚不能过大，否则会和掉血惩罚重复

建议理解为：

- `hp_point` 负责连续血量价值
- `cake_success_reward` 负责资源获取成功
- `cake_interrupt_penalty` 负责资源争夺失败

三者职责分离，避免重复建模。

## 推荐参数关系

这里先不给死值，先给参数关系建议：

```text
成功吃包奖励 > 被打断惩罚
高血浪费惩罚 >= 被打断惩罚
资源固定 bonus < 血量函数增量贡献
```

更具体一点，可以遵循：

```text
cake_success_reward : cake_interrupt_penalty : cake_waste_penalty
1.0                : 0.3 ~ 0.5              : 0.5 ~ 1.0
```

注意，这里表达的是相对强度，不是必须直接写成这些数值。

## 建议的落地形式

建议将血包相关奖励拆成三个独立 reward 项：

1. `cake_pickup_success`
2. `cake_pickup_interrupted`
3. `cake_pickup_wasted`

这样做的好处：

1. 训练监控更清晰
2. 容易单独调权重
3. 容易看出策略到底是在“不会吃包”，还是“总被打断”，还是“高血乱吃”

如果暂时不想拆 reward key，也至少要在 debug 指标里区分：

1. 成功吃包次数
2. 被打断次数
3. 高血浪费次数

## 推荐实现流程

代码层建议按以下步骤实现：

1. 保留 `hp_point` 现有逻辑不变
2. 将 `cake_pickup` 从固定分档改成基于 `f(hp)` 增量的成功奖励
3. 增加 `pending_cake_attempt` 状态
4. 增加血包被打断判定逻辑
5. 增加高血量浪费血包惩罚逻辑
6. 为成功、被打断、浪费分别加 debug 计数

## 总结

新的血包奖励设计不应再依赖固定血量分档，而应改为：

1. 使用与 `hp_point` 相同的血量函数口径
2. 用“血量函数增量 + 资源成功 bonus”定义吃包成功奖励
3. 用轻量惩罚定义“明确尝试但被打断”的失败事件
4. 用单独的浪费惩罚抑制高血乱吃

这样设计的优点是：

1. 奖励语义统一
2. 能适配后续血量函数修改
3. 更符合资源争夺行为本身的决策结构
4. 更容易调参和监控
